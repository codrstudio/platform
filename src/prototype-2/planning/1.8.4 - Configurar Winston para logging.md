# Task Plan: 1.8.4 - Configurar Winston para Logging

## Context and Objective

This task implements a **professional logging system using Winston** for the backend, replacing basic console.log statements with structured, leveled, and configurable logging. This complements the frontend error logging system and provides production-ready logging infrastructure.

**What will be implemented:**
- Install and configure Winston logger for backend
- Create logger service with multiple transports (console, file)
- Implement log levels (ERROR, WARN, INFO, DEBUG)
- Add structured logging with context metadata
- Configure environment-specific logging (dev vs prod)
- Integrate with existing error handling middleware

- SPEC-ERR-LOG-001: Platform MUST use log levels (ERROR, WARN, INFO, DEBUG)
- SPEC-ERR-LOG-002: Logs MUST include structured data (timestamp, level, category, context)
- SPEC-ERR-LOG-003: Development logging (all levels to console)
- SPEC-ERR-LOG-004: Production logging (ERROR/WARN to console, monitoring service)
- SPEC-ERR-LOG-005: Sensitive data MUST NOT be logged
- Current console.error/log statements are not production-ready

**How it integrates:**
- Replaces console.log/error in backend code
- Integrates with error handling middleware
- Provides structured logs for monitoring and debugging
- Enables log aggregation and analysis in production
- Works alongside frontend errorLogger (separate concerns)

**Business value:**

- Enables log aggregation and monitoring
- Improves troubleshooting efficiency
- Supports compliance and audit requirements
- Facilitates issue diagnosis in production

**User impact:**

**Winston Transports:**
- [Console Transport](https://github.com/winstonjs/winston/blob/master/docs/transports.md#console-transport)
  - Output to stdout/stderr
  - Colored output for readability

- [File Transport](https://github.com/winstonjs/winston/blob/master/docs/transports.md#file-transport)
  - Write logs to files
  - Separate files per level (error.log, combined.log)

- [Daily Rotate File](https://github.com/winstonjs/winston-daily-rotate-file)
  - Automatic log rotation
  - Prevents log files from growing indefinitely
  - Configurable retention period

**Winston Formats:**
- [Built-in Formats](https://github.com/winstonjs/winston#formats)
  - `winston.format.timestamp()` - Add timestamp
  - `winston.format.errors({ stack: true })` - Capture stack traces
  - `winston.format.json()` - JSON output
  - `winston.format.colorize()` - Colored console output
  - `winston.format.printf()` - Custom formatting

### Gotchas and Pitfalls

**Winston Configuration:**
- ⚠️ Winston v3 uses `createLogger` (not `new winston.Logger`)
- ⚠️ Transports are configured in `createLogger`, not added separately (v3)
- ⚠️ Levels must be specified: `levels: winston.config.npm.levels` (ERROR, WARN, INFO, HTTP, VERBOSE, DEBUG, SILLY)
- ⚠️ Default level should be 'info' in production, 'debug' in development

**File Logging:**
- ⚠️ Log directory must exist before Winston writes (create in setup)
- ⚠️ File paths should be absolute or relative to project root
- ⚠️ Log files can grow large - use rotation in production
- ⚠️ Don't commit log files to git (add to .gitignore)

**Error Handling:**
- ⚠️ If logger fails, app should not crash
- ⚠️ Wrap logger initialization in try/catch
- ⚠️ Provide fallback to console if Winston unavailable
- ⚠️ Logger errors should be non-fatal

**Sensitive Data:**
- ⚠️ Never log passwords, tokens, or sensitive user data
- ⚠️ Redact sensitive fields before logging
- ⚠️ Be careful with request/response bodies
- ⚠️ PII (Personally Identifiable Information) must be excluded

**Performance:**
- ⚠️ Excessive logging can impact performance
- ⚠️ Use appropriate log levels (don't log everything as ERROR)
- ⚠️ Consider async file transports for high-volume logging
- ⚠️ Disable DEBUG logs in production

**ESM Compatibility:**
- ⚠️ This project uses ES modules (`"type": "module"` in package.json)
- ⚠️ Use `import` syntax, not `require`
- ⚠️ Winston 3.x supports ESM but requires proper imports
- ⚠️ File paths in Node ESM need `.js` extension (even for `.ts` source)

### Error Handling Strategy

**Logger Initialization:**
```typescript
// Pattern: logger.service.ts
try {
  const logger = winston.createLogger({
    level: getLogLevel(),
    format: winston.format.combine(
      winston.format.timestamp(),
      winston.format.errors({ stack: true }),
      winston.format.json()
    ),
    transports: [
      // Console transport
      new winston.transports.Console({
        format: config.nodeEnv === 'development'
          ? winston.format.combine(
              winston.format.colorize(),
              winston.format.simple()
            )
          : winston.format.json()
      }),
      // File transports
      new winston.transports.File({
        filename: 'logs/error.log',
        level: 'error'
      }),
      new winston.transports.File({
        filename: 'logs/combined.log'
      })
    ]
  });

  export { logger };
} catch (error) {
  console.error('Failed to initialize Winston logger:', error);
  // Fallback to console
  export const logger = {
    error: console.error.bind(console),
    warn: console.warn.bind(console),
    info: console.log.bind(console),
    debug: console.log.bind(console)
  };
}
```

**Fallback Strategy:**
- If Winston fails to initialize, fall back to console methods
- Application continues running (logging is not critical)
- Error is logged to console for debugging

```typescript
// Helper to redact sensitive fields
function redactSensitive(obj: any): any {
  const sensitive = ['password', 'token', 'secret', 'apiKey'];
  const redacted = { ...obj };

  for (const key of Object.keys(redacted)) {
    if (sensitive.some(s => key.toLowerCase().includes(s))) {
      redacted[key] = '[REDACTED]';
    }
  }

  return redacted;
}

// Usage
```
