# Task Plan: 1.5.2 - Implementar heartbeat e keepalive

## Context and Objective

This task implements the heartbeat mechanism for Server-Sent Events (SSE) connections to maintain alive connections, detect disconnections promptly, and prevent proxy/firewall timeouts. Heartbeats are critical for long-lived SSE connections because:

1. **Connection Health**: Detect client disconnections without waiting for data events
2. **Proxy/Firewall Bypass**: Many proxies (nginx, HAProxy) and firewalls close idle connections after 60-120 seconds
3. **Browser Behavior**: Browsers may close connections they consider idle
4. **Network Resilience**: Detect network issues early and trigger reconnection logic

This integrates with task 1.5.1 (SSE endpoint implementation) by adding heartbeat logic to the existing `/api/events/stream` endpoint.

**Business Value**: Ensures reliable real-time communication by preventing silent connection drops and enabling early detection of network issues.

**User Impact**: Users receive events reliably without silent failures. Disconnections are detected and handled gracefully with automatic reconnection.

## Critical Context

### Documentation

**SPEC-events.md - Heartbeat Requirements**:
- **SPEC-EV-SSE-019**: Backend DEVE enviar heartbeat periódico (ex: a cada 30s)
  - Heartbeat prevents connection timeout
  - Recommended interval: 30 seconds
  - Should be configurable via environment variable

**SSE Protocol Specification**:
- SSE comments: Lines starting with `:` are ignored by EventSource
- Format: `: heartbeat\n\n` (colon, space, text, two newlines)
- Comments don't trigger `onmessage` events in the client
- Used for keepalive without semantic events

**Express Response Streams**:
- `res.write()` sends chunked data without closing connection
- `res.on('close')` detects client disconnection
- Must flush after each write for proxies: `res.flush()` (compression middleware)

### Gotchas and Pitfalls

**Proxy Buffering**:
- Proxies (nginx, HAProxy) may buffer responses
- Solution: Set `X-Accel-Buffering: no` header (already in task 1.5.1)
- Ensure `res.flush()` is called after writes if compression is enabled

**Memory Leaks**:
- MUST clear intervals when connection closes
- Failure to clear causes intervals to run indefinitely
- Store interval ID with connection for cleanup

**Interval Precision**:
- `setInterval` is not perfectly precise (can drift)
- Acceptable for heartbeat use case
- Don't use for critical timing requirements

**Connection Close Detection**:
- `req.on('close')` fires when client disconnects
- Use this to clean up intervals and remove from Map
- May fire after network issues, not immediate

**EventSource Client Behavior**:
- Browser EventSource auto-reconnects after 3-5 seconds
- Heartbeat timeout detection must be longer than this
- Recommended client timeout: 2x heartbeat interval (60s if heartbeat is 30s)

#### Step 2: Create Heartbeat Logic

**Modify**: `src/backend/src/routes/events.routes.ts`

After establishing SSE connection, start heartbeat:

```typescript
// After setting headers and storing connection
// Start heartbeat interval
const heartbeatInterval = setInterval(() => {
  try {
    // Send SSE comment (colon prefix = comment, not event)
    res.write(': heartbeat\n\n');

    // Optional: Log at debug level
    if (config.logLevel === 'debug') {
      console.log({
        timestamp: new Date().toISOString(),
        event: 'sse_heartbeat_sent',
        userId: userId,
        interval: config.sseHeartbeatInterval,
      });
    }
  } catch (error) {
    console.error('❌ Error sending heartbeat:', {
      userId,
      error: error instanceof Error ? error.message : error,
    });

    // Clear interval if write fails
    clearInterval(heartbeatInterval);
    connections.delete(userId);
  }
}, config.sseHeartbeatInterval);

// Store connection with interval ID
connections.set(userId, {
  res,
  heartbeatInterval, // Store for cleanup
  userId,
  connectedAt: new Date(),
});
```

**Why**:
- SSE comments (`: heartbeat\n\n`) keep connection alive without triggering events
- Try-catch prevents interval from crashing on write errors
- Debug logging helps troubleshooting without spam

**Pattern**: Similar to timer patterns in long-lived connections (WebSocket keepalive)

#### Step 3: Implement Cleanup on Disconnect

**Modify**: `src/backend/src/routes/events.routes.ts`

Enhance connection close handler:

```typescript
// Detect client disconnect
req.on('close', () => {
  const connection = connections.get(userId);

  if (connection) {
    // CRITICAL: Clear heartbeat interval to prevent memory leak
    clearInterval(connection.heartbeatInterval);

    // Remove from active connections
    connections.delete(userId);

    console.log({
      timestamp: new Date().toISOString(),
      event: 'sse_connection_closed',
      userId,
      duration: Date.now() - connection.connectedAt.getTime(),
    });
  }
});
```

**Why**:
- Intervals continue running even after connection closes unless explicitly cleared
- Memory leak if not cleared (interval keeps reference to `res` object)
- Log connection duration for monitoring

**Critical**: This is the most important step - prevents memory leaks

#### Step 5: Add Graceful Shutdown

**Modify**: `src/backend/src/routes/events.routes.ts` (or `app.ts`)

Clean up all connections on server shutdown:

```typescript
// Graceful shutdown handler (in app.ts or events.routes.ts)
export function closeAllSSEConnections(): void {
  console.log(`⚠️  Closing ${connections.size} SSE connections...`);

  connections.forEach((connection, userId) => {
    // Clear heartbeat interval
    clearInterval(connection.heartbeatInterval);

    // Send final comment before closing
    try {
      connection.res.write(': server-shutdown\n\n');
      connection.res.end();
    } catch (error) {
      // Ignore errors on final write
    }

    console.log(`⚠️  Closed SSE connection for user: ${userId}`);
  });

  connections.clear();
}

// Call on SIGTERM/SIGINT (in server.ts)
process.on('SIGTERM', () => {
  closeAllSSEConnections();
  // ... other cleanup
});
```

**Why**:
- Clean shutdown prevents resource leaks
- Clients receive final heartbeat before server closes
- Important for production deployments (rolling updates, scaling down)

**Pattern**: See graceful shutdown in `redis.service.ts` (`disconnect()` method)

1. **Write Errors** (connection already closed):
   ```typescript

   } catch (error) {
     // Connection closed, clear interval
     clearInterval(heartbeatInterval);
     connections.delete(userId);
   }
   ```

2. **Interval Errors** (shouldn't happen, but defensive):
   ```typescript
   setInterval(() => {
     try {
       // Heartbeat logic
     } catch (error) {
       console.error('❌ Heartbeat error:', error);
       clearInterval(heartbeatInterval);
     }
   }, interval);
   ```

3. **Cleanup Errors** (ignore, connection is dead anyway):
   ```typescript
   req.on('close', () => {
     try {
       clearInterval(connection.heartbeatInterval);
     } catch {
       // Ignore cleanup errors
     }
   });
   ```

**Error Display Pattern**: Log to console (server-side only, no client notification)

**Logging Strategy**:
- Debug level: Each heartbeat sent
- Info level: Connection established/closed
- Error level: Write failures, unexpected errors

## Implementation Notes

### Why SSE Comments Instead of Events?

SSE comments (`: heartbeat\n\n`) are preferred over events (`data: heartbeat\n\n`) because:
1. **No Client Handling Required**: Comments are silently ignored by EventSource
2. **No Event Processing**: Doesn't trigger `onmessage` handlers in client
3. **Network Efficiency**: Client doesn't need to process heartbeat data
4. **Clean Separation**: Heartbeat is transport-layer concern, not application event

### Why Per-Connection Intervals?

Each connection has its own interval instead of one global interval because:
1. **Simplicity**: No need to iterate all connections on each tick
2. **Cleanup**: Interval dies with connection (clear once, not remove from list)
3. **Flexibility**: Could have different intervals per user/portal if needed
4. **Error Isolation**: One connection error doesn't affect others

### Why 30 Seconds?

Default 30-second interval balances:
- **Too Short** (< 15s): Unnecessary network traffic, CPU usage
- **Too Long** (> 60s): Proxies may timeout, delayed disconnect detection
- **Sweet Spot** (30s):
  - Well under most proxy timeouts (60-120s)
  - Low overhead (2 messages/minute)
  - Quick disconnect detection (worst case 30s delay)

### Environment Variable Override

```bash
# .env - adjust heartbeat interval
SSE_HEARTBEAT_INTERVAL=15000  # 15 seconds (more aggressive)
SSE_HEARTBEAT_INTERVAL=60000  # 60 seconds (more relaxed)
```

Use cases:
- **15s**: High-security apps, fast disconnect detection
- **30s**: Default, balanced (recommended)
- **60s**: Low-traffic apps, reduce server load
