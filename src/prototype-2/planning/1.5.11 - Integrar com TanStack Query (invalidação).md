# Task Plan: 1.5.11 - Integrar com TanStack Query (invalidação)

## Context and Objective

This task implements automatic TanStack Query cache invalidation triggered by Server-Sent Events (SSE). When the backend publishes data-change events via SSE, the frontend will automatically invalidate relevant cached queries, ensuring the UI always displays fresh data without manual refreshing.

**What will be implemented:**
- Event-driven cache invalidation system
- Mapping between SSE events and TanStack Query keys
- Integration with existing JQEL invalidation service
- Event handler for data-change events
- Support for granular and broad invalidation strategies

**Why it's needed:**
Real-time data synchronization is critical for a responsive platform. When data changes on the server (via other users, background jobs, or n8n workflows), connected users must see updates immediately. SSE provides the notification mechanism, and this task implements the cache invalidation logic.

**How it integrates:**
- Extends SISTEMA 1.4 (JQEL + TanStack Query) with event-driven invalidation
- Complements SISTEMA 1.5 (SSE infrastructure) by adding frontend processing
- Uses existing `invalidation.ts` service patterns for consistency
- Works with hierarchical query key structure from `queryKeys.ts`

**Business value:**
- Users see real-time updates without manual refresh (improved UX)
- Reduced data staleness and user confusion
- Foundation for collaborative features (multiple users editing same data)
- Automatic sync across browser tabs/windows

**User impact:**
- Portal configurations update instantly when modified elsewhere
- Module activations reflect immediately across all connected sessions
- Real-time notifications trigger data refresh (e.g., task completion → task list refresh)

export function invalidateAfterMutation(
  queryClient: QueryClient,
  mutation: JQELQuery,
  strategy?: InvalidationStrategy
): void {
  try {
    const scope = strategy?.scope || DEFAULT_STRATEGIES[mutation.action || 'custom'];
    const { schema, mutate: entity } = mutation;

    }
  } catch (error) {
    console.error('[Invalidation] Error during cache invalidation:', error);
  }
}

### Gotchas and Pitfalls

**⚠️ Event Schema Design:**
- Events should NOT include full data payloads (SPEC-EV-AR-003)
- Events should only contain metadata: `schema`, `entity`, `recordId` (optional)
- Frontend MUST fetch data via JQEL after invalidation (SPEC-EV-FR-002)
- This design prevents large event payloads and ensures data consistency

**⚠️ Query Key Matching:**
- TanStack Query's `invalidateQueries({ queryKey })` matches **prefix** by default
- Invalidating `['backend', 'portal']` invalidates ALL portal queries
- Use `exact: true` only when you want strict key matching
- Hierarchical keys enable efficient partial invalidation

**⚠️ Race Conditions:**
- Event arrives before query is cached: No-op (query will fetch fresh data)
- Event arrives during query refetch: TanStack Query handles deduplication
- Multiple events arrive simultaneously: Each triggers invalidation independently
- Solution: TanStack Query's built-in deduplication prevents duplicate fetches

**⚠️ Error Handling:**
- Invalidation errors MUST NOT break event processing
- Always wrap invalidation in try-catch
- Log errors for debugging but continue processing other events
- Failed invalidation = stale cache (user can manually refresh)

**⚠️ Performance Considerations:**
- High-frequency events (e.g., chat messages) should use throttling
- Broad invalidations (entire schema) are expensive
- Prefer granular invalidation when `recordId` is available
- Consider debouncing multiple invalidations for same entity

**⚠️ Offline Recovery:**
- Missed events are stored in Redis Streams (backend)
- Frontend must call `/api/events/missed?lastEventId=...` on reconnect
- Process missed events as normal events (trigger invalidation)
- See Task 1.5.10 for recovery mechanism implementation

#### Step 2: Create Event Invalidation Service

**File:** `src/frontend/services/events/eventInvalidation.ts`

**Pattern:** Similar to `src/frontend/services/jqel/invalidation.ts`

**Implementation:**
```typescript
import type { QueryClient } from '@tanstack/react-query';
import type { DataChangeEvent, NotificationEvent, TaskEvent, PlatformEvent } from '../../types/events';
import { invalidateEntity, invalidateBackend } from '../jqel/invalidation';
import { isDataChangeEvent, isNotificationEvent, isTaskEvent } from '../../types/events';

/**
 * Event Invalidation Service
 *
 * Maps SSE events to TanStack Query cache invalidation.
 *
 * SPEC References:
 * - SPEC-EV-FR-001:003: Event-driven cache invalidation
 * - SPEC-DA-IN-001:008: Cache invalidation implementation
 */

/**
 * Handle data-change event
 *
 * SPEC-EV-FR-001: Use event to invalidate queries
 * SPEC-EV-FR-002: Frontend must fetch data via JQEL after invalidation
 *
 * @param queryClient - TanStack Query client
 * @param event - Data-change event from SSE
 */
export function handleDataChangeEvent(
  queryClient: QueryClient,
  event: DataChangeEvent
): void {
  try {
    const { schema, entity, recordId, action } = event.data;

    if (!schema || !entity) {
      console.warn('[EventInvalidation] Missing schema or entity:', event);
      return;
    }

    // Determine invalidation scope based on action and recordId
    const hasRecordId = recordId !== undefined;

    // Log invalidation in development
    if (import.meta.env.DEV) {
      console.log('[EventInvalidation] Processing data-change event:', {
        schema,
        entity,
        recordId,
        action,
        eventId: event.id,
      });
    }

    // Invalidate queries
    // - If recordId provided: Invalidate specific record + entity lists
    // - If no recordId: Invalidate entire entity
    if (hasRecordId) {
      invalidateEntity(queryClient, schema, entity, { recordId });
    } else {
      invalidateEntity(queryClient, schema, entity);
    }

    // Success log
    if (import.meta.env.DEV) {
      console.log('[EventInvalidation] Cache invalidated successfully');
    }
  } catch (error) {
    // CRITICAL: Invalidation errors must NOT break event processing
    console.error('[EventInvalidation] Error handling data-change event:', error, event);
  }
}

/**
 * Handle notification event
 *
 * Notifications MAY trigger invalidation if they relate to data changes.
 * Example: "Task completed" notification → invalidate task queries
 *
 * @param queryClient - TanStack Query client
 * @param event - Notification event from SSE
 */
export function handleNotificationEvent(
  queryClient: QueryClient,
  event: NotificationEvent
): void {
  try {
    // Check if notification includes data-change metadata
    const dataChange = event.data as any;
    if (dataChange?.schema && dataChange?.entity) {
      // Treat as data-change event
      handleDataChangeEvent(queryClient, {
        ...event,
        type: 'data-change',
        data: {
          schema: dataChange.schema,
          entity: dataChange.entity,
          recordId: dataChange.recordId,
          action: dataChange.action,
        },
      });
    }

    // No invalidation needed for pure notifications
  } catch (error) {
    console.error('[EventInvalidation] Error handling notification event:', error, event);
  }
}

/**
 * Handle task event
 *
 * Task status changes MAY trigger invalidation.
 * Example: Task completion → invalidate task list
 *
 * @param queryClient - TanStack Query client
 * @param event - Task event from SSE
 */
export function handleTaskEvent(
  queryClient: QueryClient,
  event: TaskEvent
): void {
  try {
    // Check if task event includes data-change metadata
    const dataChange = event.data as any;
    if (dataChange?.schema && dataChange?.entity) {
      handleDataChangeEvent(queryClient, {
        ...event,
        type: 'data-change',
        data: {
          schema: dataChange.schema,
          entity: dataChange.entity,
          recordId: dataChange.recordId,
          action: dataChange.action,
        },
      });
    }

    // Future: Invalidate task-specific queries (when task module exists)
    // Example: invalidateEntity(queryClient, 'platform', 'task', { recordId: event.data.jobId });
  } catch (error) {
    console.error('[EventInvalidation] Error handling task event:', error, event);
  }
}

/**
 * Main event invalidation handler
 *
 * Routes events to appropriate handlers based on type.
 *
 * @param queryClient - TanStack Query client
 * @param event - Platform event from SSE
 */
export function handlePlatformEvent(
  queryClient: QueryClient,
  event: PlatformEvent
): void {
  try {
    if (isDataChangeEvent(event)) {
      handleDataChangeEvent(queryClient, event);
    } else if (isNotificationEvent(event)) {
      handleNotificationEvent(queryClient, event);
    } else if (isTaskEvent(event)) {
      handleTaskEvent(queryClient, event);
    } else {
      // Unknown event type - ignore
      if (import.meta.env.DEV) {
        console.log('[EventInvalidation] Unknown event type:', event.type);
      }
    }
  } catch (error) {
    console.error('[EventInvalidation] Error processing event:', error, event);
  }
}

/**
 * Service object for export
 */
export const eventInvalidationService = {
  handleDataChangeEvent,
  handleNotificationEvent,
  handleTaskEvent,
  handlePlatformEvent,
};
```

export interface UseEventInvalidationOptions {
  /**
   * Enable/disable automatic invalidation
   * @default true
   */
  enabled?: boolean;

  /**
   * Callback after invalidation completes
   * Useful for toast notifications or custom logic

  onInvalidate?: (event: PlatformEvent) => void;

  /**
   * Filter events before processing
   * Return false to skip invalidation for specific events

  shouldHandle?: (event: PlatformEvent) => boolean;

/**

 *   useEventInvalidation();
 *   return <QueryClientProvider>...</QueryClientProvider>;
 * }
 *
 * @example
 * // With custom callback (show toast on invalidation)
 * function QueryProvider({ children }) {
 *   useEventInvalidation({
 *     onInvalidate: (event) => {
 *       if (event.type === 'data-change') {
 *         toast.info('Data updated');
 *       }
 *     }
 *   });
 *   return <QueryClientProvider>...</QueryClientProvider>;
 * }

  const { enabled = true, onInvalidate, shouldHandle } = options ?? {};

### Error Handling Strategy

**Error Types:**

1. **Parse Errors** (event data malformed)
   - **Handling:** Try-catch around `JSON.parse()`, log and continue
   - **Recovery:** Skip invalid event, process next event
   - **User Impact:** No visible error, missed update (acceptable)

2. **Missing Metadata** (schema/entity not in event)
   - **Handling:** Early return with warning log
   - **Recovery:** Skip invalidation, process next event
   - **User Impact:** No visible error, stale cache (user can refresh)

3. **Invalidation Errors** (TanStack Query failure)
   - **Handling:** Try-catch around `invalidateQueries()`, log error
   - **Recovery:** Continue processing other events
   - **User Impact:** Stale cache for specific query (rare, user can refresh)

4. **Subscription Errors** (EventSource connection lost)
   - **Handling:** Handled by Task 1.5.9 (EventSource manager)
   - **Recovery:** Automatic reconnection + missed event recovery
   - **User Impact:** Brief data staleness until reconnect

**Error Display Pattern:**
```typescript
try {
  // Invalidation logic
} catch (error) {
  // Log error for debugging
  console.error('[EventInvalidation] Error:', error, { event });

  // DO NOT show error to user
  // DO NOT throw error (would break event processing)
  // DO NOT trigger error boundary

  // Invalidation failures are non-critical:
  // - User can manually refresh
  // - Next event will trigger invalidation
  // - Query will refetch on mount
}
```

**Critical Rule:**
Invalidation errors MUST NOT break event processing or application flow. Cache invalidation is an optimization - the app must continue working even if invalidation fails.
