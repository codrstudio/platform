# Task Plan: 1.7.3 - Implementar carregamento por ambiente

## Context and Objective

This task implements **environment-specific configuration loading** to support multiple deployment environments (development, staging, production) with different settings, while maintaining a single codebase.

**What will be implemented:**
- Multi-environment .env file support (.env.development, .env.staging, .env.production)
- Environment-specific defaults and validation rules
- Environment auto-detection and override mechanisms
- Environment-aware service behavior (logging, rate limiting, security)
- Documentation for environment setup and deployment

**Why it's needed:**
Applications must run in multiple environments with different configurations:
- **Development:** Local development with lenient settings, verbose logging, HTTP allowed
- **Staging:** Pre-production environment mimicking production with test data
- **Production:** Live environment with strict security, HTTPS required, minimal logging

Currently, developers must manually edit `.env` when switching environments. This task enables automatic environment detection and environment-specific overrides.

**How it integrates:**
- Extends Task 1.7.1 (.env structure) and Task 1.7.2 (validation)
- Uses dotenv with environment-specific file loading
- NODE_ENV determines which environment file to load
- Validation rules adapt based on environment
- Services adjust behavior based on environment

**Business value:**
- Simplified deployment process (no manual .env editing)
- Reduced configuration errors across environments
- Consistent environment setup for teams
- Security enforcement in production
- Easier CI/CD pipeline integration

**User impact:**
Transparent to end users. Benefits developers and DevOps teams with streamlined environment management.

### Gotchas and Pitfalls

⚠️ **dotenv Loading Order:**
- dotenv does NOT automatically load environment-specific files
- Must explicitly load `.env.{NODE_ENV}` files
- Later files override earlier ones (NOT merged)
- Use `dotenv.config()` multiple times with different paths

⚠️ **NODE_ENV Bootstrap Problem:**
- NODE_ENV must be set BEFORE loading environment files
- Chicken-and-egg: Can't read NODE_ENV from .env to determine which .env to load
- Solution: NODE_ENV must come from system environment or package.json scripts

⚠️ **Frontend vs Backend Environment:**
- Frontend (Vite): Automatically loads `.env.{mode}` based on `--mode` flag
- Backend (Node.js): Must manually implement environment file loading
- Default modes: `development` (dev), `production` (build)

⚠️ **Environment File Security:**
- `.env` files should NEVER be committed (except .env.example)
- `.env.local` provides local overrides without git tracking
- Production secrets MUST NOT be in version control
- Use environment-specific files as templates, deploy with real secrets

⚠️ **Variable Precedence:**
- System environment variables > .env files
- This allows CI/CD to override file-based config
- Useful for secrets injection in deployment pipelines

⚠️ **Vite Environment Variables:**
- Vite embeds env vars at BUILD time (not runtime)
- Frontend builds are environment-specific artifacts
- Must build separately for each environment
- Cannot change VITE_* vars after build

## Technical Specification

### Architecture

```
Environment Configuration Loading Flow:

┌─────────────────────────────────────────────────┐
│ 1. System Environment                           │
│    - NODE_ENV set by: npm script | system var  │
│    - Example: NODE_ENV=staging npm run dev     │
└────────────────────┬────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│ 2. Load Environment Files (dotenv)              │
│    - Load order (priority: low → high):        │
│      1. .env (base)                             │
│      2. .env.local (local overrides)            │
│      3. .env.{NODE_ENV} (environment-specific)  │
│      4. .env.{NODE_ENV}.local (local env)       │
│    - Later files override earlier              │
└────────────────────┬────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│ 3. Validate Configuration (env.ts)              │
│    - Environment-aware validation               │
│    - Stricter rules for production              │
│    - Exit if validation fails                   │
└────────────────────┬────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────┐
│ 4. Configure Services                           │
│    - Logging: verbose in dev, minimal in prod   │
│    - Rate limiting: lenient in dev, strict in prod│
│    - Security: relaxed in dev, strict in prod   │
└─────────────────────────────────────────────────┘
```

```typescript
import dotenv from 'dotenv';
import { resolve, dirname } from 'path';
import { fileURLToPath } from 'url';
import { existsSync } from 'fs';

// Get __dirname equivalent in ES modules
const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

/**
 * Load environment files in priority order
 *
 * Priority (highest to lowest):
 * 1. .env.{NODE_ENV}.local (local environment overrides)
 * 2. .env.{NODE_ENV} (environment-specific)
 * 3. .env.local (local overrides)
 * 4. .env (base configuration)
 *
 * SPEC-CF-PS-017:019: Environment-based configuration loading
 */
function loadEnvironmentFiles(): void {
  const envDir = resolve(__dirname, '../..');
  const nodeEnv = process.env.NODE_ENV || 'development';

  // Define files to load (order matters - later overrides earlier)
  const envFiles = [
    '.env',                          // Base config (always loaded)
    '.env.local',                    // Local overrides
    `.env.${nodeEnv}`,              // Environment-specific
    `.env.${nodeEnv}.local`,        // Local environment overrides
  ];

  console.log(`\n🔧 Loading environment configuration for: ${nodeEnv}\n`);

  // Load each file if it exists
  envFiles.forEach(file => {
    const filePath = resolve(envDir, file);
    if (existsSync(filePath)) {
      console.log(`   ✓ Loading ${file}`);
      dotenv.config({ path: filePath, override: true });
    } else {
      // Don't warn about missing .local files (optional)
      if (!file.includes('.local')) {
        console.log(`   ⚠ ${file} not found (using defaults)`);
      }
    }
  });

  console.log(''); // Blank line for readability
}

// Load environment files BEFORE validation
loadEnvironmentFiles();
```

```typescript
import morgan from 'morgan';
import { config } from '../config/env.js';

/**
 * HTTP request logging middleware
 *
 * Environment-aware logging:
 * - Development: detailed logs with colors
 * - Staging: combined format, JSON structure
 * - Production: minimal logs, JSON structure
 */

// Define format based on environment
const getLogFormat = (): string => {
  switch (config.nodeEnv) {
    case 'development':
      return 'dev'; // Colorized, detailed output
    case 'staging':
      return 'combined'; // Standard Apache combined log
    case 'production':
      return 'combined'; // Standard Apache combined log
    default:
      return 'combined';
  }
};

// Create logger with environment-specific format
export const loggerMiddleware = morgan(getLogFormat(), {
  // Skip logging for health checks in production (reduce noise)
  skip: (req, _res) => {
    if (config.nodeEnv === 'production' && req.path === '/api/health') {
      return true;
    }
    return false;
  },
});
```

## Troubleshooting

### Environment not loading

**Problem:** Application doesn't use environment-specific settings

**Solution:**
1. Verify NODE_ENV is set: `echo $NODE_ENV`
2. Check file exists: `ls -la .env.*`
3. Check console logs during startup for loaded files
4. Ensure environment file has correct name

### Secrets validation fails in production

**Problem:** `JWT_SECRET must contain both letters and numbers`

**Solution:**
- Production requires strong secrets (alphanumeric mix)
- Generate secure random secret: `openssl rand -base64 32`
- Update .env file with generated secret

### Frontend not using correct environment

**Problem:** Frontend uses wrong API URL

**Solution:**
1. Frontend builds are environment-specific
2. Rebuild with correct mode: `npm run build:staging`
3. Verify `.env.{mode}` file exists
4. Check build output shows correct VITE_API_URL

### HTTPS required errors in staging/production

**Problem:** `N8N_BASE_URL must use HTTPS in production`

**Solution:**
- Staging and production REQUIRE HTTPS
- Update URLs to use https:// protocol
- Use HTTP only in development

### Error Handling Strategy

**Environment File Not Found:**
- Log warning for missing `.env.{NODE_ENV}` file
- Fall back to .env base configuration
- Continue startup (file is optional)

**NODE_ENV Not Set:**
- Default to 'development' with warning
- Log warning: "NODE_ENV not set, defaulting to development"

**Invalid NODE_ENV Value:**
- Validation error during startup
- List valid values: development, staging, production
- Exit with code 1

**Environment-Specific Validation Failures:**
- Collect all validation errors
- Display with environment context
- Exit with code 1 before server starts

**Production Security Violations:**
- HTTP URLs in production: ERROR
- Weak secrets in production: ERROR
- Missing Redis password in production: WARNING (not error)
- Placeholder secrets in production: ERROR
