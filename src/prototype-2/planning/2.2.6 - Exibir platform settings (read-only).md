# Task Plan: 2.2.6 - Exibir platform settings (read-only)

## Context and Objective

This task implements a read-only view of platform-level configuration settings within the Setup module. Platform settings are environment variables defined in the backend's `.env` file that control core infrastructure aspects like n8n URLs, Redis connections, Node environment, and API endpoints. Unlike portal/module/instance configurations (which are editable via JQEL), platform settings require server access to modify.

**Why it's needed:** Administrators need visibility into platform configuration to troubleshoot issues, verify environment setup, and understand the platform's infrastructure. Without this view, they must SSH into the server or check logs, which is inefficient and not always feasible in production.

**How it integrates:** This is a standalone page/section within the Setup module that queries a backend endpoint exposing safe platform configuration. It includes health checks for critical services (n8n, Redis, Backend) to provide operational status at a glance.

**Business value:** Reduces troubleshooting time by providing immediate visibility into platform configuration and service health. Enables administrators to verify environment setup without server access.

**User impact:** Administrators can quickly check platform configuration, verify environment (dev/staging/prod), and see service health status without leaving the UI or accessing server logs.

### Gotchas and Pitfalls

- ⚠️ **Never expose secrets**: JWT_SECRET, N8N_SHARED_SECRET, PLATFORM_SHARED_SECRET, and Redis passwords must NOT be returned by the API. Backend must filter these out.

- ⚠️ **Mask sensitive parts**: Redis password in REDIS_URL should be masked (e.g., `redis://***@localhost:6379`). Backend must sanitize before sending.

- ⚠️ **Read-only enforcement**: Frontend must clearly indicate settings are read-only. No input fields, only display values. Include prominent message about how to edit (.env file + restart).

- ⚠️ **Health check timeouts**: n8n health check should timeout after 5 seconds max to avoid hanging the UI. Use Promise.race() or request timeout.

- ⚠️ **CORS considerations**: Platform settings endpoint must have CORS headers for frontend access. Should already be handled by global CORS middleware.

- ⚠️ **Authentication**: Platform settings endpoint should require authentication (JWT validation). Don't expose to unauthenticated users.

```

    ↓
HTTP GET /api/platform-settings
    ↓
Backend: platform-settings.routes.ts
    ↓
Read config object (from env.ts)
    ↓
Run health checks:
  - checkN8nHealth() → HTTP GET n8n/healthz
  - checkRedisHealth() → Redis PING
  - checkBackendHealth() → Always true (self-check)
    ↓
Filter sensitive values:
  - Remove JWT_SECRET, N8N_SHARED_SECRET, PLATFORM_SHARED_SECRET
  - Mask redisPassword
    ↓
Return JSON:
  {
    settings: { nodeEnv, port, frontendUrl, ... },
    health: { n8n: true/false, redis: true/false, backend: true }
  }
    ↓
Frontend: Cache response in TanStack Query
    ↓
PlatformSettings Component: Render settings + health
    ↓
Poll every 30s for health status updates
```

### Error Handling Strategy

**Error Types:**

1. **Backend Offline / Network Error**
   - Handling: Catch in TanStack Query `onError`
   - Display: Error state with retry button
   - Recovery: User clicks retry, or auto-retry after 30s

2. **Authentication Failure (401)**
   - Handling: Redirect to login or show auth error
   - Display: "You must be logged in to view platform settings"
   - Recovery: User logs in

3. **Service Health Check Failure**
   - Handling: Backend returns `false` for service
   - Display: Red XCircle badge with "Unreachable" status
   - Recovery: User investigates service (backend logs, service restart)

4. **Missing/Invalid Data in Response**
