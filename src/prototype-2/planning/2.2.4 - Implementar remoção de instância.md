# Task Plan: 2.2.4 - Implementar remoção de instância

## Context and Objective

Implement the Instance deletion functionality for the Setup Module, allowing administrators to remove instances they no longer need. This task implements a confirmation dialog pattern to prevent accidental deletions and ensures proper cleanup of instance data.

**Business Value:** Enables administrators to clean up unused configurations, reducing clutter and potential confusion while maintaining system hygiene.

**User Impact:** Users can safely remove instances with a clear confirmation step, preventing accidental data loss while maintaining confidence in their ability to manage configurations.

  ```typescript
  export function useDeleteInstance() {
    const queryClient = useQueryClient();
    return useOptimisticMutation<Instance, string>({
      mutationFn: async (instanceId: string) => {
        return deleteRecord<Instance>(
          'backend',
          'instance',
          { instanceId: { $eq: instanceId } }
        );
      },
      onSuccess: () => {
        // Invalidate all instance queries
        queryClient.invalidateQueries({
          queryKey: queryKeys.backend.instances(),
        });
      },
    });
  }
  ```

### Reusable Code Examples

**Deletion Flow Pattern:**
```typescript
const [isDeleteDialogOpen, setIsDeleteDialogOpen] = useState(false);
const [instanceToDelete, setInstanceToDelete] = useState<string | null>(null);
const deleteInstance = useDeleteInstance();

const handleDeleteClick = (instanceId: string) => {
  setInstanceToDelete(instanceId);
  setIsDeleteDialogOpen(true);
};

const handleConfirmDelete = async () => {
  if (!instanceToDelete) return;

  try {
    await deleteInstance.mutateAsync(instanceToDelete);
    toast({ title: 'Success', description: 'Instance deleted successfully' });
    setIsDeleteDialogOpen(false);
  } catch (error) {
    toast({
      title: 'Error',
      description: error.message || 'Failed to delete instance',
      variant: 'destructive'
    });
    // Keep dialog open for retry
  }
};
```

### Gotchas and Pitfalls

- ⚠️ **Confirmation required**: Per SPEC-MS-FB-003, deletion MUST show confirmation dialog before proceeding.
- ⚠️ **No consequences listed**: Per SPEC-MS-FB-004, confirmation should list consequences (e.g., "Configuration data will be lost"), but for instances this is straightforward.
- ⚠️ **Destructive action**: Use `variant="destructive"` for delete buttons to signal danger.
- ⚠️ **Focus trap**: AlertDialog automatically traps focus, ensuring keyboard users can't accidentally tab out.
- ⚠️ **Optimistic updates**: The mutation hook uses optimistic updates, so the instance disappears immediately from the list.
- ⚠️ **Query invalidation**: On success, all instance queries are automatically invalidated and refetched.
- ⚠️ **Dialog auto-close**: Only close dialog on success, keep open on error to allow retry.

### Existing Patterns to Follow

- **Confirmation dialogs**: See SPEC-MS-FB-001:004 - Always confirm destructive actions
- **Error feedback**: See SPEC-MS-FB-008:011 - Clear error messages with recovery options
- **Success feedback**: See SPEC-MS-FB-005:007 - Toast notification, auto-dismiss
- **Focus management**: AlertDialog handles focus trap automatically
- **Accessibility**: AlertDialog has built-in ARIA attributes for screen readers

### Data Flow

```
User clicks delete button on instance card

1. InstanceCard.tsx:
   - User clicks "Delete" button (Trash2 icon)
   - setIsDeleteDialogOpen(true)
   - Dialog appears

2. User sees confirmation dialog:
   - Title: "Delete Instance?"
   - Description: "Are you sure you want to delete instance '{instanceId}'? This action cannot be undone."
   - Buttons: Cancel, Delete

3a. User clicks Cancel:
   - setIsDeleteDialogOpen(false)
   - Dialog closes
   - No mutation called

3b. User clicks Delete (Confirm):
   - Button shows spinner, disabled
   - Call deleteInstance.mutateAsync(instanceId)

4. JQEL mutation sent to backend:
   POST /api/jqel
   {
     schema: "backend",
     mutate: "instance",
     action: "delete",
     where: { instanceId: { $eq: instanceId } }
   }

5. Backend processes deletion:
   - Validates permission (if applicable)
   - Removes instance from instances.json
   - Returns success/error

6. Mutation onSuccess:
   - Invalidate instance queries (list refreshes)
   - Show success toast
   - Close dialog
   - Instance disappears from list

7. Mutation onError:
   - Show error toast
   - Re-enable delete button
   - Keep dialog open for retry
```

1. **Identify Instance to Delete**
   - User views instance list (task 2.2.1)
   - User hovers over instance card
   - Delete button (Trash2 icon) becomes visible/highlighted

2. **Initiate Deletion**
   - User clicks "Delete" button

   - Focus moves to dialog (trapped)
   - Background slightly dimmed (overlay)

3. **Review Confirmation**
   - User reads dialog title: "Delete Instance?"
   - User reads description: "Are you sure you want to delete instance '{instanceId}'? This action cannot be undone."
   - User sees warning icon (AlertTriangle)
   - User considers decision

4a. **Cancel Deletion**
   - User clicks "Cancel" button OR presses Escape
   - Dialog closes
   - Focus returns to delete button
   - No data changed

4b. **Confirm Deletion**
   - User clicks "Delete" button
   - Delete button shows spinner, becomes disabled
   - Cancel button becomes disabled
   - System sends deletion request

5. **Handle Result**
   - Success:
     - Dialog auto-closes
     - Toast appears: "Instance deleted successfully"
     - Instance disappears from list (animated)
     - List reflows
   - Error:
     - Delete button re-enables
     - Cancel button re-enables
     - Toast appears: "Failed to delete: {error}"
     - User can retry or cancel

### Error Handling Strategy

**Error Types:**

- **Network errors**:
  - Display: Toast "Failed to delete instance. Check your connection."
  - Recovery: Keep dialog open, user can retry

- **Permission errors**:
  - Display: Toast "You don't have permission to delete this instance."
  - Recovery: Close dialog, user contacts admin

- **Instance not found** (already deleted):
  - Display: Toast "Instance no longer exists."
  - Recovery: Close dialog, refresh list (shows updated state)

- **Server validation errors**:
  - Display: Toast with server error message
  - Recovery: Keep dialog open, user can retry or cancel

**Error Display Pattern:**
```typescript
try {
  await deleteInstance.mutateAsync(instanceId);
  toast({ title: 'Success', description: 'Instance deleted' });
  setIsDeleteDialogOpen(false);
} catch (error) {
  const errorMessage = error instanceof Error
    ? error.message
    : 'An unexpected error occurred';

  toast({
    title: 'Failed to delete instance',
    description: errorMessage,
    variant: 'destructive',
  });
  // Dialog stays open for retry
}
```
