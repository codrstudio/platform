# Task Plan: 1.8.3 - Criar ModuleErrorBoundary

## Context and Objective

This task implements **Module-Level Error Boundaries**, the finest-grained tier in the three-tier error boundary system (Global → Portal → Module). Module error boundaries isolate errors within individual module components, preventing one module's failure from affecting the rest of the portal.

**What will be implemented:**
- Create a specialized `ModuleErrorFallback` UI component
- Create a wrapper component or HOC for wrapping module content
- Integrate error boundary at module loading/rendering level
- Provide module-specific recovery actions
- Ensure module errors don't break portal layout

**Why it's needed:**
- SPEC-ERR-BOUND-008: Complex modules MAY have their own error boundaries
- SPEC-ERR-BOUND-009: Module errors MUST NOT break entire portal
- SPEC-ERR-BOUND-010: Module-specific fallback UI required
- Enables graceful degradation of individual features
- Allows portal shell to remain functional when module fails

**How it integrates:**
- Wraps module components/routes individually
- Sits below portal boundary, above component code
- Uses existing ErrorBoundary component with `level="module"`
- Most granular error isolation in the system

**Business value:**
- Maximum resilience - single module failure doesn't affect other modules
- Improved user experience - partial functionality better than complete failure
- Enables progressive enhancement approach
- Reduces impact of third-party module bugs

**User impact:**
- Users see module-specific error message instead of portal-wide error
- Rest of portal remains functional (navigation, other modules)
- Can continue using working modules while one fails
- Clear indication which module has the problem

  - Don't over-use - strategic placement only
  - Module boundaries are appropriate for complex features

**Component Composition:**

  - Error boundaries as wrapper components
  - Use children prop for flexible composition
  - HOC pattern for reusable error handling

### Gotchas and Pitfalls

**Module Boundary Placement:**
- ⚠️ Place boundary at module entry point, not every component
- ⚠️ Don't wrap every component - defeats the purpose
- ⚠️ Balance between isolation and excessive error handling
- ⚠️ Complex modules (dashboard, kanban) should have boundaries
- ⚠️ Simple modules (button, icon) should NOT have boundaries

**Layout Considerations:**
- ⚠️ Module error should not take full screen (portal layout remains)
- ⚠️ Use inline/card-sized error display
- ⚠️ Preserve portal navigation and structure
- ⚠️ Error should fit in module's allocated space

**Recovery Actions:**
- ⚠️ "Try Again" may not work if error is persistent
- ⚠️ Consider "Hide Module" or "Reload Page" as alternatives
- ⚠️ No navigation - portal should remain active
- ⚠️ Keep it simple - complex recovery logic can fail too

**Module Context:**
- ⚠️ Module boundaries need moduleId for logging
- ⚠️ May need to pass via context or props
- ⚠️ Without moduleId, logging is less useful
- ⚠️ Consider React Context for module metadata

**Performance:**
- ⚠️ Each boundary adds a class component wrapper
- ⚠️ Don't create boundary per list item - one per feature
- ⚠️ Lazy loading works with error boundaries

### User Journey

1. **User Interacts with Portal**
   - Portal loaded successfully
   - Multiple modules rendered in portal
   - Navigation and layout working

2. **Error Occurs in Module**
   - User triggers action in specific module
   - Module component throws rendering error
   - Module boundary catches it

3. **Fallback Displayed (Inline)**
   - Module content replaced with error UI
   - Portal layout remains intact (nav, other modules still visible)
   - User sees inline error message
   - Other modules continue functioning

4. **User Chooses Recovery:**

   **Option A: Try Again**
   - User clicks "Try Again"
   - Error boundary resets state
   - Module attempts to re-render
   - If successful, module content restored
   - If error persists, fallback shows again

   **Option B: Use Other Features**
   - User ignores failed module
   - Uses other modules in portal
   - Failed module shows error state
   - User can report issue or try later

   **Option C: Navigate Away**
   - User navigates to different portal/route
   - Failed module unmounts
   - If user returns, module loads fresh

5. **Developer Debugging (Dev Mode)**
   - Developer sees inline error details
   - Expands to view stack trace
   - Identifies failing component
   - Fixes issue and tests

### Error Handling Strategy

**Error Types:**
- **Module rendering errors:** Caught by ErrorBoundary
  - Display ModuleErrorFallback inline
  - Log with category 'error-boundary', moduleId in context
  - Portal remains functional

- **Module loading errors:** NOT caught by boundary (handled by module loader)
  - Lazy loading failures → Suspense fallback
  - Not error boundary responsibility

- **Module route errors:** Caught if boundary wraps route
  - Display inline error
  - Portal navigation remains active

**Error Display Pattern:**
```typescript
// Pattern: ModuleErrorFallback.tsx
import type { FallbackProps } from '../../types/errorBoundary';

export function ModuleErrorFallback({ error, resetError }: FallbackProps) {
  const handleRetry = () => {
    resetError();
  };

  return (
    <div
      className="flex flex-col items-center justify-center p-6 text-center"
      role="alert"
      aria-live="polite"
    >
      {/* Small Error Icon */}
      <div className="mb-2 text-destructive">
        <svg
          width="24"
          height="24"
          viewBox="0 0 24 24"
          fill="none"
          stroke="currentColor"
          strokeWidth="2"
          strokeLinecap="round"
          strokeLinejoin="round"
          aria-hidden="true"
        >
          <circle cx="12" cy="12" r="10" />
          <line x1="12" y1="8" x2="12" y2="12" />
          <line x1="12" y1="16" x2="12.01" y2="16" />
        </svg>
      </div>

      {/* Title */}
      <h3 className="text-base font-semibold mb-2">
        Failed to Load Module
      </h3>

      {/* Message */}
      <p className="text-sm text-muted-foreground mb-4">
        This module encountered an error. Try reloading.
      </p>

      {/* Action */}
      <button
        onClick={handleRetry}
        className="inline-flex items-center justify-center rounded-md bg-primary px-3 py-1.5 text-sm font-medium text-primary-foreground hover:bg-primary/90 focus:outline-none focus:ring-2 focus:ring-primary focus:ring-offset-2"
      >
        Try Again
      </button>

      {/* Dev Details - Inline */}
      {import.meta.env.DEV && (
        <details className="mt-4 text-left w-full">
          <summary className="cursor-pointer text-xs text-muted-foreground hover:text-foreground">
            Error Details
          </summary>
          <pre className="mt-2 text-xs bg-muted p-3 rounded-md overflow-auto max-h-32">
            {error.stack || error.message}
          </pre>
        </details>
      )}
    </div>
  );
}
```

**Convenience Wrapper Pattern:**
```typescript
// Pattern: ModuleErrorBoundary.tsx
import { type ReactNode, type ErrorInfo } from 'react';
import { ErrorBoundary } from './ErrorBoundary';
import { ModuleErrorFallback } from './ModuleErrorFallback';
import { logError } from '../../services/logging/errorLogger';

interface ModuleBoundaryProps {
  children: ReactNode;
  moduleId?: string;
  onError?: (error: Error, errorInfo: ErrorInfo) => void;
}

export function ModuleErrorBoundary({
  children,
  moduleId,
  onError
}: ModuleBoundaryProps) {
  const handleError = (error: Error, errorInfo: ErrorInfo) => {
    // Log with moduleId context
    logError(error, {
      category: 'error-boundary',
      level: 'ERROR',
      context: {
        level: 'module',
        moduleId,
        componentStack: errorInfo.componentStack
      }
    });

    // Call custom handler if provided
    onError?.(error, errorInfo);
  };

  return (
    <ErrorBoundary
      level="module"
      fallback={ModuleErrorFallback}
      onError={handleError}
    >
      {children}
    </ErrorBoundary>
  );
}
```
