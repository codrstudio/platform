# Task Plan: 1.8.5 - Implementar níveis de log (ERROR, WARN, INFO, DEBUG)

## Context and Objective

This task implements comprehensive logging level management for the error handling system. The platform needs a structured logging system with four severity levels (ERROR, WARN, INFO, DEBUG) that provides appropriate visibility in development vs. production environments while maintaining security and performance.

**What will be implemented:**
- Extend existing `errorLogger.ts` with complete log level support
- Add DEBUG level logging with development-only visibility
- Implement environment-aware log output (dev vs. production)
- Add structured log entry formats for all levels
- Create convenient helper functions for each log level

**Why it's needed:**
The existing `errorLogger.ts` has basic ERROR/WARN/INFO support but lacks:
1. Full DEBUG level implementation
2. Consistent structured logging across all levels
3. Helper functions that match specification requirements
4. Complete environment-aware output control

**How it integrates:**
- Used by all error boundaries, JQEL hooks, SSE handlers, and module loaders
- Integrates with existing `logError()`, `logWarning()`, `logInfo()` functions
- Provides foundation for future monitoring service integration (SPEC-EH-LO-010)

**Business value:**
- Developers get detailed debugging information in development
- Production logs remain clean and focused on actionable errors
- Consistent log structure enables future analytics and monitoring
- Security maintained by filtering sensitive data from logs

**User impact:**
- Indirect: Better debugging leads to faster bug fixes and improved stability
- No direct UI impact (internal logging system)

### Gotchas and Pitfalls

**⚠️ Production Log Exposure**
- DEBUG and INFO logs can expose implementation details
- MUST NOT log in production environment except ERROR/WARN
- Stack traces only in development (SPEC-EH-DEV-001)

**⚠️ Console Method Mismatch**
- Using wrong console method (e.g., `console.error()` for INFO) affects browser DevTools filtering
- Each level should use appropriate console method for proper categorization

**⚠️ TypeScript Strictness**
- `LogLevel` type must include 'DEBUG' for type safety
- Update `LogErrorOptions` interface to accept DEBUG level
- Ensure exhaustive switch statements handle all levels

**⚠️ Performance in Production**
- Even if logs don't output, string concatenation still happens
- Consider early returns for disabled log levels
- Avoid expensive operations in log context construction

export function logError(error: Error, options: LogErrorOptions): void {
  const { category, level = 'ERROR', context = {} } = options;

  const logEntry: ErrorLogEntry = {
    timestamp: new Date().toISOString(),
    level,
    category,
    message: error.message,
    error: {
      name: error.name,
      message: error.message,
      ...(import.meta.env.DEV && { stack: error.stack })
    },
    context
  };

  // Environment-aware output with appropriate console method
  if (import.meta.env.DEV) {
    // In dev: Output all levels with appropriate console method
    switch (level) {
      case 'ERROR':
        console.error(`[${level}] ${category}:`, logEntry);
        break;
      case 'WARN':
        console.warn(`[${level}] ${category}:`, logEntry);
        break;
      case 'INFO':
        console.info(`[${level}] ${category}:`, logEntry);
        break;
      case 'DEBUG':
        console.debug(`[${level}] ${category}:`, logEntry);
        break;
    }
  } else if (level === 'ERROR' || level === 'WARN') {
    // In prod: Only ERROR and WARN
    if (level === 'ERROR') {
      console.error(`[${level}] ${category}:`, logEntry);
    } else {
      console.warn(`[${level}] ${category}:`, logEntry);
    }
  }

  // TODO: Send to monitoring service in production (SPEC-EH-LO-010)

}
