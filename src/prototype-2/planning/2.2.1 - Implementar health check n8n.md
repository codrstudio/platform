# Task Plan: 2.2.1 - Implementar health check n8n

## Context and Objective

Implement n8n Backbone health check functionality for the Setup Module. This allows administrators to monitor the connectivity and availability of the n8n Backbone service, which is critical for platform operations (authentication, JQEL queries, business logic).

**Business Value**: Provides real-time visibility into n8n service status, enabling proactive issue detection and faster troubleshooting during platform configuration.

**User Impact**: Administrators in the Setup Module can immediately see if n8n is accessible and operational, preventing configuration mistakes when the Backbone is unavailable.

**Integration**: This health check will be displayed in the Platform Settings view of the Setup Module (SPEC-MS-PS-010:016) alongside Redis and Backend health indicators.

```typescript
// Backend: Service method pattern from n8nProxy.service.ts
private async callWorkflow<T>(
  path: string,
  data: any,
  options?: { timeout?: number }
): Promise<T> {
  const timeout = options?.timeout || this.defaultTimeout;
  const url = `${this.baseUrl}${path}`;

  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), timeout);

  try {
    const response = await fetch(url, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'X-Platform-Key': this.platformKey,
      },
      body: JSON.stringify(data),
      signal: controller.signal,
    });

    if (!response.ok) {
      throw new Error(`Request failed: ${response.statusText}`);
    }

    return await response.json();
  } catch (error: any) {
    if (error.name === 'AbortError') {
      throw new Error('Request timeout');
    }
    throw error;
  } finally {
    clearTimeout(timeoutId);
  }
}
```

### Gotchas and Pitfalls

- ⚠️ n8n may not have a standard `/healthz` endpoint - might need to use a lightweight workflow webhook as health probe
- ⚠️ Timeout is critical - don't let health checks hang indefinitely (use 5-10 second timeout)
- ⚠️ Too frequent polling can add unnecessary load - balance freshness vs. performance (60 second interval recommended)
- ⚠️ Don't expose sensitive information (credentials, internal IPs) in health check responses
- ⚠️ Handle DNS resolution failures and network errors gracefully
- ⚠️ CORS may block health checks if n8n is on different domain - ensure proper configuration

### Error Handling Strategy

**Error Types:**
- **Network errors** (n8n unreachable): Display red indicator with "Service unavailable" message
- **Timeout errors**: Display yellow indicator with "Service slow or unreachable" message
- **HTTP errors** (4xx, 5xx): Display red indicator with status code and message
- **DNS resolution failures**: Display red indicator with "Cannot resolve hostname" message

**Error Display Pattern:**
```typescript
// In HealthIndicator component
if (error) {
  return (
    <div className="rounded-lg border border-red-200 bg-red-50 p-4">
      <div className="flex items-center gap-2">
        <XCircle className="h-5 w-5 text-red-600" />
        <span className="font-medium text-red-900">{service} - Down</span>
      </div>
      <p className="mt-1 text-sm text-red-700">{error.message}</p>
    </div>
  );
}
```

**Backend Error Handling:**
```typescript
// In health.routes.ts
try {
  const result = await n8nProxyService.healthCheck();
  return res.json(result);
} catch (error: any) {
  // Map errors to status
  if (error.message.includes('timeout')) {
    return res.status(503).json({ status: 'down', error: 'Timeout' });
  }
  if (error.message.includes('unreachable')) {
    return res.status(503).json({ status: 'down', error: 'Unreachable' });
  }
  return res.status(503).json({ status: 'down', error: error.message });
}
```
