# Task Plan: 1.7.8 - Validar chave de plataforma

## Context and Objective

This task implements validation of the `X-Platform-Key` header for incoming requests from n8n → Backend, completing the mutual authentication between n8n Backbone and the Platform. This validation ensures that only authorized n8n instances can trigger backend endpoints.

**What will be implemented**: Middleware to validate `X-Platform-Key` header on endpoints that n8n calls (if any), using constant-time comparison to prevent timing attacks.

**Why it's needed**: Prevents unauthorized systems from impersonating n8n and calling backend APIs. Without validation, any system knowing backend URLs could trigger actions, creating security vulnerabilities.

**How it integrates**:
- Complements task 1.7.7 which sends headers in Backend → n8n direction
- Backend already has `PLATFORM_SHARED_SECRET` in config (from env.ts)
- Creates new middleware for header validation
- Applied to routes that n8n calls (currently none, but infrastructure for future)

**Business value**: Ensures only authorized n8n instances can invoke backend endpoints, protecting business logic and data from unauthorized access.

**User impact**: Transparent to users - security hardening happens at the infrastructure level without affecting user experience.

### Gotchas and Pitfalls

**Timing Attacks**:
- ⚠️ MUST use constant-time comparison (SPEC-CF-AM-013)
- Simple `===` comparison leaks timing information
- Attacker can guess secret character-by-character
- Solution: `crypto.timingSafeEqual(bufferA, bufferB)`

**Buffer Length Mismatch**:
- `timingSafeEqual` throws error if buffer lengths differ
- MUST check lengths before comparison
- Different length = definitely not equal (safe to reject early)

**Header Case Sensitivity**:
- HTTP headers are case-insensitive per RFC 7230
- Express normalizes to lowercase: `req.headers['x-platform-key']`
- Value comparison MUST be case-sensitive (SPEC-CF-AM-012)
- Secret values are case-sensitive strings

**Empty or Missing Header**:
- Missing header: `req.headers['x-platform-key']` is `undefined`
- Empty header: `req.headers['x-platform-key']` is `''`
- Both MUST be rejected (SPEC-CF-AM-014)
- Validate presence before comparing

**Error Message Disclosure**:
- ⚠️ Don't reveal if header is missing vs. wrong value
- Generic error: "Unauthorized" (no details)
- Prevents attackers from learning system state
- Log detailed info server-side only

**Development vs. Production**:
- ⚠️ Validation must work in ALL environments
- No "skip in development" logic
- Security cannot be disabled
- Use valid secrets in development too

#### Step 2: Implement Header Extraction and Validation

**File**: `src/backend/src/middleware/platformAuth.middleware.ts`

**Implementation**:
```typescript
export const platformAuthMiddleware = (
  req: Request,
  res: Response,
  next: NextFunction
): void => {
  // Extract header (Express normalizes to lowercase)
  const receivedKey = req.headers['x-platform-key'];

  // Validate header presence (SPEC-CF-AM-014)
  if (!receivedKey || receivedKey === '') {
    // Log security event (server-side only)
    console.warn('⚠️  Platform authentication failed: Missing or empty X-Platform-Key header', {
      timestamp: new Date().toISOString(),
      ip: req.ip,
      path: req.path,
      method: req.method,
    });

    // Return generic error (no details to client)
    return res.status(401).json({
      error: 'Unauthorized',
    });
  }

  // Get expected secret from config
  const expectedKey = config.platformSharedSecret;

  // Validate using constant-time comparison (prevent timing attacks)
  const isValid = compareSecrets(receivedKey, expectedKey);

  if (!isValid) {
    // Log security event
    console.warn('⚠️  Platform authentication failed: Invalid X-Platform-Key value', {
      timestamp: new Date().toISOString(),
      ip: req.ip,
      path: req.path,
      method: req.method,
    });

    // Return generic error
    return res.status(401).json({
      error: 'Unauthorized',
    });
  }

  // Success - log and continue
  if (config.logLevel === 'debug') {
    console.log('✅ Platform authentication successful', {
      timestamp: new Date().toISOString(),
      ip: req.ip,
      path: req.path,
      method: req.method,
    });
  }

  // Continue to next middleware/route handler
  next();
};
```

**Why**:
- Validates presence before comparison (avoid comparing undefined)
- Logs all authentication attempts for security monitoring
- Generic error prevents information leakage
- Debug logging helps troubleshooting without spam

**Pattern**: Similar to rate limiting and security middleware in codebase.

#### Step 3: Implement Constant-Time Comparison Helper

**File**: `src/backend/src/middleware/platformAuth.middleware.ts`

**Add helper function before middleware**:
```typescript
/**
 * Compare two secrets using constant-time comparison
 *
 * Prevents timing attacks where attacker measures response time
 * to guess secret character-by-character.
 *
 * SPEC-CF-AM-013: Validação DEVE usar comparação constant-time
 *
 * @param received - Secret from request header
 * @param expected - Secret from config
 * @returns true if secrets match, false otherwise
 */
function compareSecrets(received: string, expected: string): boolean {
  try {
    // Convert strings to buffers for timingSafeEqual
    const bufferReceived = Buffer.from(received, 'utf8');
    const bufferExpected = Buffer.from(expected, 'utf8');

    // CRITICAL: timingSafeEqual throws if lengths differ
    // Check lengths first (different length = definitely not equal)
    if (bufferReceived.length !== bufferExpected.length) {
      return false;
    }

    // Constant-time comparison (SPEC-CF-AM-013)
    // Returns true if buffers are identical, false otherwise
    return timingSafeEqual(bufferReceived, bufferExpected);
  } catch (error) {
    // Log error but don't expose to client
    console.error('❌ Error in secret comparison:', {
      timestamp: new Date().toISOString(),
      error: error instanceof Error ? error.message : error,
    });

    // Fail closed - reject on error
    return false;
  }
}
```

**Why**:
- Prevents timing attacks (SPEC-CF-AM-013)
- Handles length mismatch safely (timingSafeEqual requirement)
- Fail closed on errors (rejects rather than allowing)
- Try-catch prevents crashes from invalid inputs

**Critical**: This is the security core of the middleware - must be correct.

## Implementation Notes

### Why Constant-Time Comparison?

**Problem**: Simple string comparison (`===`) leaks timing information:
```typescript
// ❌ VULNERABLE to timing attacks
if (receivedKey === expectedKey) { ... }
```

**Attack**: Attacker measures response time:
1. Try "a..." → Fast rejection (1st char wrong)
2. Try "x..." → Also fast (1st char wrong)
3. Try "y..." → Slightly slower (1st char matches, 2nd char wrong!)
4. Attacker learns 1st char is "y", repeats for next char

**Solution**: `timingSafeEqual` compares ALL bytes regardless:
```typescript
// ✅ SECURE - always takes same time
timingSafeEqual(bufferA, bufferB)
```

**Why it matters**: Attacker can guess a 32-character secret in ~256 * 32 = 8,192 requests instead of 256^32 attempts.

### Why Buffer Conversion?

`timingSafeEqual` requires `Buffer` or `Uint8Array`:
```typescript
// Convert string → buffer
const bufferA = Buffer.from(stringA, 'utf8');
const bufferB = Buffer.from(stringB, 'utf8');

// Then compare buffers
timingSafeEqual(bufferA, bufferB);
```

**Why not strings?**: Node.js API design - forces explicit encoding, avoids encoding bugs.

### Why Check Length First?

`timingSafeEqual` throws if lengths differ:
```javascript
timingSafeEqual(Buffer.from('abc'), Buffer.from('abcd'))
// Error: Input buffers must have the same length
```

**Solution**: Check lengths first:
```typescript
if (bufferA.length !== bufferB.length) {
  return false; // Safe to reject early - different lengths
}
return timingSafeEqual(bufferA, bufferB);
```

**Timing concern?**: No - length comparison is fast and uniform, attacker already knows secret length (min 32 chars per SPEC).

### Why Generic Error Messages?

**Bad**:
```json
{"error": "X-Platform-Key header is missing"}
{"error": "X-Platform-Key value is incorrect"}
```

**Problem**: Attacker learns:
1. Header name expected
2. Whether they're sending it correctly
3. Whether value is close

**Good**:
```json
{"error": "Unauthorized"}
```

**Result**: Attacker gets no useful information, must guess blindly.
