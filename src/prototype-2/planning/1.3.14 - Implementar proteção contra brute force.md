# Task Plan: 1.3.14 - Implementar proteção contra brute force

## Context and Objective

This task implements brute force attack protection for the authentication system, specifically targeting login attempts. Brute force protection is a critical security layer that prevents attackers from systematically trying multiple password combinations to gain unauthorized access.

**What will be implemented:**
- Backend middleware to track failed login attempts per username/IP combination
- Progressive delay mechanism that increases wait time after consecutive failures
- Temporary account lockout after exceeding failure threshold
- Redis-based storage for attempt tracking with automatic TTL expiration
- Integration with `/api/1/auth/login` endpoint to enforce protection
- Configurable thresholds and lockout durations via environment variables

**Why it's needed:**
According to SPEC-authentication.md (SPEC-AU-LI-025:026), multiple failed login attempts MAY result in rate limiting, and this MUST be implemented in the Backbone or Backend. This prevents automated attacks where malicious actors attempt thousands of password combinations to compromise accounts.

**How it integrates:**
- Executes as middleware BEFORE the login handler processes credentials
- Tracks attempts in Redis with composite keys (username + IP)
- Returns HTTP 429 (Too Many Requests) when threshold exceeded
- Works alongside task 1.3.13 (general IP-based rate limiting)
- Complements token rotation (1.3.7) and reuse detection (1.3.8) for defense-in-depth

**Business value:**
- Protects user accounts from unauthorized access attempts
- Prevents credential stuffing attacks (using leaked passwords from other breaches)
- Reduces server load from malicious automated login attempts
- Maintains platform reputation and user trust
- Compliance with security best practices (OWASP Top 10)

**User impact:**
- Legitimate users: Minimal impact - small delay only after multiple wrong passwords
- Malicious actors: Cannot brute force passwords - locked out after threshold
- Account owners: Protection against unauthorized access even with weak passwords
- System administrators: Visibility into attack patterns via structured logging

  - Negative TTL (-1) = no expiration, (-2) = key doesn't exist
- [Redis Key Naming](https://redis.io/docs/manual/keyspace/#key-naming-conventions)
  - Use colons for hierarchy: `brute_force:username:ip`
  - Enables pattern-based operations (e.g., KEYS, SCAN)

**OWASP Authentication Guidelines:**
- [OWASP Authentication Cheat Sheet](https://cheatsheetsecurity.org/cheatsheets/authentication-cheat-sheet.html#account-lockout)
  - Recommends 3-5 failed attempts before lockout
  - Lockout duration: 15-30 minutes
  - Track by username + IP (not just IP to avoid lockout of legitimate users on shared IPs)

### Gotchas and Pitfalls

**⚠️ Tracking Key Design:**
- **Problem:** Tracking only by IP locks out all users on shared networks (offices, cafes)
- **Solution:** Use composite key `username:ip` - locks specific account from specific IP only
- **Trade-off:** More sophisticated attackers can rotate IPs, but prevents casual brute force

**⚠️ Redis Connection Failures:**
- **Problem:** If Redis is down, brute force protection fails silently
- **Solution:** Implement fallback behavior - DENY access on Redis errors (fail secure)
- **Alternative:** Could allow with logging, but less secure

**⚠️ Race Conditions:**
- **Problem:** Multiple concurrent requests could bypass increment logic
- **Solution:** Use Redis atomic operations (INCR, EXPIRE together)
- **Implementation:** Use Redis MULTI/EXEC transactions or Lua scripts

**⚠️ Account Enumeration:**
- **Problem:** Different error messages reveal if username exists
- **Solution:** Return same error message regardless of username validity
- **Message:** "Too many failed attempts. Try again later." (generic)

**⚠️ TTL Management:**
- **Problem:** Setting attempt count and TTL separately creates race condition
- **Solution:** Use SETEX or set TTL only on first attempt (INCR + EXPIRE if NX)
- **Pattern:**
  ```typescript
  // Increment attempt count
  const count = await redis.incr(key);

  // Set TTL only if first attempt (count === 1)
  if (count === 1) {
    await redis.expire(key, windowDuration);
  }
  ```

**⚠️ Legitimate Users Locked Out:**
- **Problem:** User forgets password, gets locked out legitimately
- **Solution:**
  - Provide clear messaging with retry time
  - Implement "Forgot Password" flow as alternative
  - Consider CAPTCHA after 2-3 attempts instead of hard lockout

**⚠️ Progressive Delay vs Hard Lockout:**
- **Option A - Progressive Delay:** After each failure, add delay (1s, 2s, 5s, 10s...)
- **Option B - Hard Lockout:** After N failures, block completely for X minutes
- **Recommendation:** Combine both - progressive delays first, then hard lockout
- **Implementation:** Store both attempt count AND first attempt timestamp

### Modules and Responsibilities

**BruteForceProtectionService** (`services/bruteForceProtection.service.ts`)
- **Responsibility:** Core logic for attempt tracking and validation
- **Methods:**
  - `checkAttempt(username: string, ip: string): Promise<AttemptResult>`
    - Validates if attempt is allowed
    - Returns: `{ allowed: boolean, attempts: number, retryAfter?: number, message?: string }`
  - `recordFailure(username: string, ip: string): Promise<void>`
    - Increments failure counter
    - Updates timestamps
  - `clearAttempts(username: string, ip: string): Promise<void>`
    - Removes attempt record (called on successful login)
  - `getAttemptInfo(username: string, ip: string): Promise<AttemptData | null>`
    - Retrieves current attempt information (for debugging/monitoring)

**bruteForceMiddleware** (`middleware/bruteForce.middleware.ts`)
- **Responsibility:** Express middleware that enforces brute force protection
- **Behavior:**
  - Extracts username from `req.body.username` and IP from `req.ip`
  - Calls `bruteForceService.checkAttempt(username, ip)`
  - If blocked: responds with 429 and terminates request
  - If allowed: calls `next()` to proceed to login handler

**Configuration** (`config/env.ts`)
- **New Variables:**
  - `BRUTE_FORCE_MAX_ATTEMPTS` - Number of failures before lockout (default: 5)
  - `BRUTE_FORCE_LOCKOUT_DURATION` - Lockout time in seconds (default: 900 = 15 min)
  - `BRUTE_FORCE_WINDOW_DURATION` - Time window for counting attempts (default: 600 = 10 min)

### State Management

**Redis Keys:**
```
brute_force:{username}:{ip}
```

**Value Structure:**
```typescript
{
  attempts: number,           // Number of failed attempts
  firstAttempt: string,       // ISO timestamp of first attempt in window
  lastAttempt: string,        // ISO timestamp of most recent attempt
  lockedUntil?: string        // ISO timestamp when lockout expires (if locked)
}
```

**TTL Strategy:**
- **During Attempt Window:** TTL = BRUTE_FORCE_WINDOW_DURATION (e.g., 10 minutes)
  - Resets on each failed attempt to extend window
- **During Lockout:** TTL = BRUTE_FORCE_LOCKOUT_DURATION (e.g., 15 minutes)
  - Fixed duration from lockout trigger
- **On Success:** Key deleted immediately

**Error Types and Responses:**

       code: 'service_unavailable',

   }

2. **Too Many Attempts**
   ```typescript
   // HTTP 429 Too Many Requests

     code: 'too_many_attempts',

   if (!req.body.username) {
     console.warn('⚠️ Brute force check skipped - missing username');
     next();  // Continue to normal validation
     return;
   }
   ```

4. **Account Enumeration Protection**
   ```typescript
   // ALWAYS return same message for locked accounts
   // Do NOT reveal if username exists or not
   message: 'Too many failed login attempts. Please try again later.'
   // NOT: 'Account alice is locked' ← reveals username existence
   ```

**Error Display Pattern:**
```typescript
// From auth.routes.ts pattern
console.error('❌ Error in brute force protection:', {
  timestamp: new Date().toISOString(),
  username: req.body.username,  // OK to log
  ip: req.ip,
  error: error.message,
  // NEVER log: password, tokens
});
```
