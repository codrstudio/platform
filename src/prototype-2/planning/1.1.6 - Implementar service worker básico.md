# Task Plan: 1.1.6 - Implementar service worker básico

## Context and Objective

This task implements a comprehensive service worker for prototype-2, establishing the foundation for Progressive Web App (PWA) capabilities. The service worker will enable offline functionality, intelligent asset caching, and improved performance through strategic resource management.

**Why it's needed**: Service workers are mandatory per SPEC-A-PWA-002 and enable the platform to function as a true PWA. They intercept network requests, cache critical assets, and provide offline fallbacks when network connectivity is unavailable. This is essential for enterprise applications where users may experience intermittent connectivity.

**Business value**: Enables offline-first architecture, reduces data usage through intelligent caching, improves perceived performance by serving cached assets instantly, and provides a seamless user experience even with poor network conditions. Critical for mobile users and remote workers.

**Integration**: The service worker integrates with Vite (task 1.1.3) through vite-plugin-pwa, serves the manifest.json (task 1.1.5), and enables lazy loading of modules (task 1.1.7). It works alongside the backend proxy for API requests and supports the SSE system for real-time events (System 1.5).

### Gotchas and Pitfalls
- ⚠️ **Workbox Auto-Generation**: With `strategy: 'generateSW'` (default), vite-plugin-pwa generates service worker automatically. Do NOT manually edit `public/sw.js` as it will be overwritten. Use `workbox` config in vite.config.ts instead.
- ⚠️ **Cache Names**: Workbox uses versioned cache names automatically. Do NOT hardcode cache names like 'platform-v1' - Workbox manages this.
- ⚠️ **navigateFallback**: When configuring offline fallback page, use `navigateFallback: '/offline.html'` in workbox config, not in manifest
- ⚠️ **API Caching**: NEVER cache authentication endpoints (/api/1/auth/*) or sensitive data. Use NetworkOnly strategy.
- ⚠️ **SSE Connections**: Server-Sent Events cannot be cached. Use NetworkOnly strategy for /api/events
- ⚠️ **Module Chunks**: Dynamically imported modules (lazy-loaded) need runtime caching with CacheFirst strategy
- ⚠️ **Development Mode**: Service worker is NOT active in dev mode by default. Use `devOptions.enabled: true` to test in dev
- ⚠️ **HTTPS Requirement**: Service workers only work on HTTPS (or localhost). Production deployment MUST use HTTPS.

### Data Flow

```
Application Startup:
main.tsx → registerServiceWorker() → workbox-window → Register SW → Install → Activate

Network Request Flow:
Browser Request → Service Worker Intercept → Check Cache → Apply Strategy → Return Response
                                                ↓
                                         [Strategy Decision Tree]
                                                ↓
        ┌───────────────────────────────────────────────────────────┐
        │                                                             │
    Static Assets          API Calls           Modules           Special Routes
    (CacheFirst)       (NetworkFirst)      (CacheFirst)         (Varies)
        ↓                   ↓                   ↓                    ↓
    Return cached      Try network first   Cache on load      Auth: NetworkOnly
    or fetch          with cache fallback  then serve cached  SSE: NetworkOnly
                                                                Offline: fallback.html
```

### State Management

Service worker registration state:
- **Not registered**: Initial state, SW registration pending
- **Installing**: SW is downloading and installing
- **Installed**: SW installed but waiting to activate
- **Activating**: SW taking control of pages
- **Activated**: SW active and controlling navigation
- **Update available**: New SW version detected

State managed via workbox-window `Workbox` class events.

#### 3. Configure Runtime Caching Strategies
- Modify: `src/prototype-2/frontend/vite.config.ts` → `workbox.runtimeCaching` array
- Add multiple caching strategies:

**Strategy 1 - API Data (NetworkFirst):**
```typescript
{
  urlPattern: /^https?:\/\/.*\/api\/(?!1\/auth|events).*/,
  handler: 'NetworkFirst',
  options: {
    cacheName: 'api-cache',
    networkTimeoutSeconds: 10,
    expiration: { maxEntries: 50, maxAgeSeconds: 5 * 60 }, // 5 minutes
    cacheableResponse: { statuses: [0, 200] }
  }
}
```
**Rationale**: Data freshness important but offline access needed. Excludes auth/events endpoints.

**Strategy 2 - Authentication & Events (NetworkOnly):**
```typescript
{
  urlPattern: /^https?:\/\/.*\/api\/(1\/auth|events).*/,
  handler: 'NetworkOnly'
}
```
**Rationale**: Auth tokens and SSE connections must never be cached (SPEC-A-PWA-022).

**Strategy 3 - Module Chunks (CacheFirst):**
```typescript
{
  urlPattern: /\/assets\/.*\.(js|css)$/,
  handler: 'CacheFirst',
  options: {
    cacheName: 'module-cache',
    expiration: { maxEntries: 100, maxAgeSeconds: 30 * 24 * 60 * 60 }, // 30 days
    cacheableResponse: { statuses: [0, 200] }
  }
}
```
**Rationale**: Lazy-loaded modules are versioned and immutable, cache aggressively (SPEC-A-PWA-008).

**Strategy 4 - External Resources (StaleWhileRevalidate):**
```typescript
{
  urlPattern: /^https?:\/\/(fonts\.googleapis\.com|fonts\.gstatic\.com|cdn\.jsdelivr\.net).*/,
  handler: 'StaleWhileRevalidate',
  options: {
    cacheName: 'external-cache',
    expiration: { maxEntries: 30, maxAgeSeconds: 365 * 24 * 60 * 60 }, // 1 year
    cacheableResponse: { statuses: [0, 200] }
  }
}
```
**Rationale**: External resources (fonts, CDN assets) change rarely, serve stale while revalidating.

**Strategy 5 - Images (CacheFirst with size limit):**
```typescript
{
  urlPattern: /\.(png|jpg|jpeg|svg|gif|webp)$/,
  handler: 'CacheFirst',
  options: {
    cacheName: 'image-cache',
    expiration: { maxEntries: 60, maxAgeSeconds: 30 * 24 * 60 * 60 }, // 30 days
    cacheableResponse: { statuses: [0, 200] }
  }
}
```
**Rationale**: Images are static and bandwidth-heavy, cache aggressively to reduce data usage.

- Pattern: Each strategy targets specific URL patterns with appropriate handler

### Error Handling Strategy

**Error Types and Handling:**

**Registration Errors:**
- Browser doesn't support SW: Log warning, continue without offline support
- Registration fails: Log error, retry once after 60 seconds
- Update fails: Log error, notify user to refresh manually

**Caching Errors:**
- Cache quota exceeded: Workbox automatically prunes old entries
- Network timeout (10s): Serve cached response if available
- No cached response and offline: Serve offline.html fallback

**Error Display Pattern:**
```typescript
try {
  await registerServiceWorker();
} catch (error) {
  console.error('[SW] Registration failed:', error);
  // Don't show UI error - offline support is enhancement, not requirement
  // App continues to work without SW
}
```

**Principle**: Service worker failures should NEVER break the application. Offline support is progressive enhancement.
