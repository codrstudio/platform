# Task Plan: 1.1.1 - Criar estrutura de pastas

## Context and Objective

This is the foundational task for prototype-2, establishing the complete project structure for a modular platform with three layers: Frontend (React 19), Backend (Express), and integration with Backbone (n8n). The folder structure must support:

- Independent frontend and backend applications
- Shared TypeScript types and utilities
- Module-based architecture with lazy loading
- PWA capabilities with service worker
- Clear separation of concerns across all layers

This structure enables all subsequent tasks in the Platform Foundation increment (Systems 1.1-1.10) and establishes conventions that will guide the entire implementation.

### Conventions to Follow

Based on the specifications (SPEC-architecture.md, SPEC-concepts.md, SPEC-modules.md):

**Naming Conventions:**
- Use kebab-case for directories (e.g., `modules/`, `app-components/`)
- Use PascalCase for component files (e.g., `PortalRouter.tsx`)
- Use camelCase for utility files (e.g., `jqelClient.ts`)
- Module IDs are kebab-case (e.g., `chat`, `setup`, `app-components`)

**File Structure Patterns:**
- Group by feature/domain, not by type (colocation principle)
- Modules are self-contained with their own components/, hooks/, types/
- Shared code goes in shared/ directory
- Configuration files at project roots

**Import/Export Patterns:**
- Modules export via index.ts (single entry point)
- Use named exports for clarity
- Barrel exports (index.ts) for public API

**Architecture Boundaries:**
- Frontend NEVER imports from Backend
- Backend NEVER imports from Frontend
- Shared code is the only cross-boundary import
- Each layer has its own node_modules and package.json

### Gotchas and Pitfalls

**Vite Requirements:**
- Vite REQUIRES index.html at the project root (not inside src/)
- Public assets must be in public/ directory at Vite root
- Service worker must be properly scoped (typically at root)

**Module System:**
- Dynamic imports require proper path resolution
- Lazy-loaded modules need separate chunks (Vite handles this with dynamic imports)
- Module manifests must be easily discoverable

**TypeScript Shared Code:**
- Shared types must be compiled independently
- Frontend and backend need separate tsconfig.json
- Consider using project references for better IDE support

**Environment Variables:**
- Frontend: Vite requires VITE_ prefix for env vars
- Backend: Standard process.env
- Never commit .env files

**PWA Considerations:**
- manifest.json location affects scope
- Service worker scope is limited to its directory and below
- Both should typically be at public root

### Data Flow

**Development Flow:**
1. Shared types are defined in `shared/types/`
2. Frontend and Backend import from `shared/` using TypeScript project references
3. Both layers compile independently but share type definitions
4. No runtime dependency between frontend and backend

**Module Loading Flow:**
1. Portal determines active modules from backend config
2. Frontend's module registry loads modules dynamically
3. Each module is a separate chunk (Vite code splitting)
4. Module exports via index.ts → registry → router/components

**Configuration Access Flow:**
1. Backend stores configs in `backend/src/config/*.json`
2. Frontend accesses via JQEL with schema="backend"
3. Backend's jqelProcessor handles "backend" schema queries
4. Returns data from JSON files

### Modules and Responsibilities

**Frontend Structure:**
- `core/` - Platform infrastructure (routing, module system, portals)
- `modules/` - Feature modules (lazy-loaded, independent)
- `components/` - Shared UI components
- `providers/` - React Context providers for global state
- `services/` - API client layer (JQEL, Auth, SSE)
- `hooks/` - Shared React hooks
- `types/` - Frontend-specific types

**Backend Structure:**
- `routes/` - HTTP endpoint definitions
- `middleware/` - Express middleware chain
- `services/` - Business logic and external service integration
- `config/` - JSON configuration storage
- `types/` - Backend-specific types
- `utils/` - Helper functions

**Shared Structure:**
- `types/` - Type definitions used by both frontend and backend
- `constants/` - Shared constants and enums
- `utils/` - Pure functions with no platform dependencies

### State Management

**Global State (React Context):**
- AuthProvider - Authentication state
- ThemeProvider - Theme preferences (light/dark, brand color)
- QueryProvider - TanStack Query client
- SSEProvider - Server-sent events connection

**Data State (TanStack Query):**
- All server data via JQEL
- Cache managed by TanStack Query
- Invalidation via SSE events

**Local State:**
- Component-specific state via useState/useReducer
- Form state via React Hook Form
- Module-specific state within module boundaries
