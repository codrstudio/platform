# Task Plan: 1.2.7 - Criar componente ProtectedRoute

## Context and Objective

This task implements a `ProtectedRoute` component to secure routes that require authentication and optionally specific permissions. The component acts as a wrapper for routes, checking authentication status before rendering protected content and redirecting unauthenticated users to login.

**Business Value:**
- Prevents unauthorized access to protected resources
- Provides consistent authentication checks across all secured routes
- Enables granular permission-based access control
- Improves security posture by centralizing auth logic

**User Impact:**
- Users without valid authentication are automatically redirected to login
- Users without required permissions see appropriate error messages
- Seamless experience for authenticated users with proper permissions

**Integration:**
This component integrates with:
- Sistema 1.3 (Authentication) - requires AuthContext to check user auth status
- React Router - wraps Route components to control rendering
- Future authorization system - validates permissions via `/api/1/auth/authorize`

### Gotchas and Pitfalls

- ⚠️ **AuthContext Dependency:** This component CANNOT be implemented until AuthContext exists (task 1.3.3). The component will fail at runtime without it.
- ⚠️ **React Router v6+:** Uses `<Navigate>` for redirects, not `<Redirect>` from v5
- ⚠️ **State Location:** Must preserve original location when redirecting to login so user can return after auth
- ⚠️ **Loading State:** Must handle loading state while auth status is being determined (avoid flash of wrong content)
- ⚠️ **Permission Check:** Permission validation should be optional - not all protected routes need it
- ⚠️ **Error Boundaries:** Should work within error boundaries - don't throw errors, render fallback UI

### Architecture

    └── routing/
        ├── ProtectedRoute.tsx

### Data Flow

```
User navigates to protected route
         ↓
ProtectedRoute component renders
         ↓
Check isLoading from AuthContext
         ↓
    [if loading] → Show loading indicator
         ↓
    [if not loading]
         ↓
Check isAuthenticated from AuthContext
         ↓
    [if false] → Navigate to /login with return location
         ↓
    [if true]
         ↓
Check requiredPermission prop
         ↓
    [if none] → Render children
         ↓
    [if exists] → (Future) Call /api/1/auth/authorize
         ↓
    [if authorized] → Render children
         ↓
    [if not authorized] → Show 403 Forbidden page
```

export interface ProtectedRouteProps {
  /**
   * Content to render when user is authenticated and authorized
   */
  children: React.ReactNode;

  /**
   * Whether authentication is required to access this route
   * @default true
   */

  /**

   * Format: {operation}.{entity}[.{action}]

  /**
   * Custom loading indicator while checking authentication
   * If not provided, shows default loading message
   */
  fallback?: React.ReactNode;

  /**
   * Custom component to show when user lacks required permission
   * If not provided, shows default 403 Forbidden message
   */
  forbiddenFallback?: React.ReactNode;

  /**
   * Redirect path for unauthenticated users
   * @default "/login"
   */
  redirectTo?: string;
}
```

#### 2. Create ProtectedRoute Component

**Create:** `src/frontend/src/core/routing/ProtectedRoute.tsx`

**Implementation Details:**

```typescript
import React from 'react';
import { Navigate, useLocation } from 'react-router-dom';
import { useAuth } from '@/providers/AuthProvider';
import type { ProtectedRouteProps } from './types';

/**
 * ProtectedRoute component
 *
 * Wraps route content and controls access based on authentication
 * and optionally authorization status.
 *
 * Usage:
 * ```tsx
 * <Route path="/dashboard" element={
 *   <ProtectedRoute>
 *     <DashboardPage />
 *   </ProtectedRoute>
 * } />
 *
 * // With permission check
 * <Route path="/admin" element={
 *   <ProtectedRoute requiredPermission="admin.access">
 *     <AdminPage />
 *   </ProtectedRoute>
 * } />
 * ```
 *
 * Specification: SPEC-R-RP-001:008, SPEC-AU-MA-014:018
 */
export default function ProtectedRoute({
  children,
  requireAuth = true,
  requiredPermission,
  fallback,
  forbiddenFallback,
  redirectTo = '/login',
}: ProtectedRouteProps): React.ReactElement {
  const { isAuthenticated, isLoading, user } = useAuth();
  const location = useLocation();

  // Step 1: Handle loading state
  // While checking authentication, show loading indicator
  // SPEC-R-RP-001: Wait for auth check before deciding
  if (isLoading) {
    return (
      <div>
        {fallback || (
          <div style={{ padding: '2rem', textAlign: 'center' }}>
            <p>Loading...</p>
          </div>
        )}
      </div>
    );
  }

  // Step 2: Check authentication requirement
  // SPEC-R-RP-004: Redirect to login if not authenticated
  // SPEC-AU-MA-017: Use Navigate with state to preserve return location
  if (requireAuth && !isAuthenticated) {
    return (
      <Navigate
        to={redirectTo}
        state={{ from: location }}
        replace
      />
    );
  }

  // Step 3: Check permission requirement (if specified)
  // SPEC-AU-MA-016: CAN verify specific permissions
  // Note: Full permission checking will be implemented in Sistema 1.3
  // For now, this is a placeholder for future integration with /api/1/auth/authorize
  if (requiredPermission && user) {
    // TODO (Sistema 1.3): Implement permission check via /api/1/auth/authorize
    // For now, just check if user object exists (authenticated users pass)
    // const hasPermission = await checkPermission(user, requiredPermission);

    // Placeholder: Assume authenticated users have permission
    // This will be replaced with actual API call in authentication tasks
    const hasPermission = true;

    if (!hasPermission) {
      // SPEC-AU-MA-018: Show 403 without permission
      return (
        <div>
          {forbiddenFallback || (
            <div style={{ padding: '2rem', textAlign: 'center' }}>
              <h1>403 - Forbidden</h1>
              <p>You do not have permission to access this resource.</p>
              <p>Required permission: <code>{requiredPermission}</code></p>
            </div>
          )}
        </div>
      );
    }
  }

  // Step 4: Render protected content
  // User is authenticated and authorized
  return <>{children}</>;
}
```

**Pattern:** Standard HOC/wrapper component pattern for route protection

### Error Handling Strategy

**Error Types:**

1. **AuthContext Not Found:**
   - **Cause:** Component used before AuthProvider is mounted
   - **Handling:** useAuth() hook should throw descriptive error
   - **User Impact:** Development-time error, caught in development

2. **Navigation State Lost:**
   - **Cause:** Browser back/forward with lost location state
   - **Handling:** Default to home/dashboard if `state.from` is undefined
   - **User Impact:** Minimal - redirected to safe default

3. **Permission Check Failure:**
   - **Cause:** API call to /api/1/auth/authorize fails
   - **Handling:** Treat as permission denied (fail closed)
   - **User Impact:** Shown 403 page, can retry or contact support

**Error Display Pattern:**

```typescript
// Simple inline error display for 403
<div style={{ padding: '2rem', textAlign: 'center' }}>
  <h1>403 - Forbidden</h1>
  <p>You do not have permission to access this resource.</p>
</div>

// Can be replaced with custom forbiddenFallback prop
```

### Implementation Notes

**Why This Approach:**
1. **Declarative:** Wraps route content, making protection explicit in route definitions
2. **Flexible:** Optional permission checking, custom fallbacks
3. **Spec-Compliant:** Follows SPEC-R-RP-* and SPEC-AU-MA-* requirements exactly
4. **Future-Proof:** Permission system designed for easy integration with authorize endpoint

**Alternative Approaches Considered:**
- **HOC Pattern:** Could wrap entire route definitions, but less explicit in JSX
- **Hook Pattern:** Could expose `useProtectedRoute()` hook, but requires manual redirect logic
- **Router-Level Guards:** Could extend React Router, but adds unnecessary complexity

**Chosen approach balances simplicity, readability, and spec compliance.**
