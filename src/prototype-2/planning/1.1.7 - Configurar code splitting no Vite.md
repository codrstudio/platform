# Task Plan: 1.1.7 - Configurar code splitting no Vite

## Context and Objective

This task configures advanced code splitting strategies in Vite to optimize bundle sizes and implement lazy loading for the modular architecture of prototype-2. Code splitting ensures that modules load on-demand, reducing initial bundle size and improving application performance.

**Why it's needed**: The platform's modular architecture (SPEC-A-LL-001 to SPEC-A-LL-010) requires lazy loading of modules to meet strict performance targets: initial bundle < 200KB gzipped, landing page < 1s load on 3G, and module chunks < 500KB gzipped. Without proper code splitting, all modules would be loaded upfront, violating these requirements and defeating the purpose of the modular system.

**Business value**: Users experience fast initial load times regardless of how many modules are installed in the system. Only the modules active in a specific portal are downloaded, and only when that portal is accessed. This enables the platform to scale to dozens of modules without performance degradation.

**Integration**: Code splitting configuration works with the module loading system (SISTEMA 2.1), enables lazy routes (SISTEMA 1.2), supports PWA caching strategies (SISTEMA 1.1), and ensures vendor libraries are efficiently shared across all modules.

**User impact**: Users on slow connections (3G) can still use the platform productively. The initial page loads in under 1 second, and modules load progressively as needed. This is critical for mobile users and users in regions with limited connectivity.

### Conventions to Follow

- **Naming Convention for Chunks**:
  - Vendor chunks: `{library-name}-vendor` (e.g., `react-vendor`, `ui-vendor`)
  - Module chunks: `modules/{moduleId}` (auto-generated by dynamic import)
  - Core chunks: `{feature-name}` (e.g., `core`, `routing`)

- **Chunk Organization Strategy**:
  - Separate vendor libraries from application code
  - Group rarely-changing dependencies (React, UI libs) together
  - Keep module code separate for lazy loading
  - Core platform code in main bundle

- **Import Pattern for Lazy Loading**:
  ```typescript
  // Module loading with dynamic import (generates separate chunk)
  const module = await import(`./modules/${moduleId}/index.tsx`);

  // Route lazy loading with React.lazy
  const ChatRoom = React.lazy(() => import('./modules/chat/components/ChatRoom'));
  ```

- **Build Configuration Pattern**:
  - `cssCodeSplit: true` - CSS per async chunk for module isolation
  - `sourcemap: false` in production - reduces bundle size
  - `reportCompressedSize: false` - faster builds (gzip calculation expensive)
  - `target: 'es2020'` - modern browsers only, smaller bundles

### Gotchas and Pitfalls

- **Over-splitting can hurt performance**: Too many small chunks increase HTTP requests (HTTP/2 helps but overhead still exists)
- **Vendor chunk sharing critical**: If each module bundles React separately, total size explodes
- **Dynamic import path must be specific enough**: `import(`./${folder}/${file}.ts`)` works, but `import(variable)` doesn't generate chunks
- **manualChunks vs. automatic splitting**: Manual control prevents duplicate dependencies across chunks
- **Tree-shaking limitations**: Some libraries (like Lodash) need named imports to tree-shake properly
- **CSS code splitting**: `cssCodeSplit: true` can cause FOUC (Flash of Unstyled Content) if not using CSS-in-JS or Tailwind
- **Chunk size warnings**: Vite warns at 500KB, but this is configurable and per SPEC-A-LL-009
- **Service Worker considerations**: Each chunk needs appropriate caching strategy (see SPEC-A-PWA-008 and 009)

```typescript
// In vite.config.ts plugins array
// ADD: Custom plugin to enforce chunk size limits (optional)
{
  name: 'enforce-chunk-size',
  generateBundle(options, bundle) {
    const MAX_CHUNK_SIZE = 500 * 1024; // 500KB in bytes
    const oversized = [];

    for (const [fileName, chunk] of Object.entries(bundle)) {
      if (chunk.type === 'chunk' && chunk.code) {
        const size = Buffer.byteLength(chunk.code);
        if (size > MAX_CHUNK_SIZE) {
          oversized.push({ fileName, size: Math.round(size / 1024) });
        }
      }
    }

    if (oversized.length > 0) {
      console.warn('⚠️ Oversized chunks detected:');
      oversized.forEach(({ fileName, size }) => {
        console.warn(`  - ${fileName}: ${size}KB (max: 500KB)`);
      });
      // Uncomment to fail build in CI:
      // throw new Error('Build failed: chunks exceed size limit');
    }
  }
}
```

**Rationale**: Early detection of oversized chunks prevents performance regressions. Warning in development, optional error in CI/CD.

### Error Handling Strategy

**Error Types**:

1. **Chunk Load Failure** (network error, 404, etc.)
   - **Cause**: Module file deleted, network failure, CDN issue
   - **Handling**: Retry mechanism with exponential backoff
   - **User Feedback**: Toast notification "Failed to load module. Retrying..."
   - **Recovery**: Offer manual refresh button if retries fail

2. **Parse Error** (malformed JavaScript)
   - **Cause**: Corrupted file, build error, incompatible browser
   - **Handling**: Error boundary catches, logs to console
   - **User Feedback**: Modal with error details and browser compatibility check
   - **Recovery**: Hard reload or clear cache

3. **Oversized Chunk** (development warning)
   - **Cause**: Module includes large dependencies not in vendor chunks
   - **Handling**: Build warning, optionally fail CI build
   - **User Feedback**: Console warning during build
   - **Recovery**: Refactor module to extract large dependencies

**Error Display Pattern**:
```typescript
// Example error boundary for lazy-loaded modules
// File: src/core/modules/ModuleErrorBoundary.tsx (future task)

class ModuleErrorBoundary extends React.Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, errorInfo) {
    // Log to monitoring service
    console.error('Module load failed:', error, errorInfo);

    // Check if chunk load error
    if (error.name === 'ChunkLoadError') {
      // Attempt retry after delay
      setTimeout(() => {
        window.location.reload();
      }, 2000);
    }
  }

  render() {
    if (this.state.hasError) {
      return (
        <div className="p-4 border border-destructive rounded-lg">
          <h2>Failed to load module</h2>
          <p>Please check your connection and try again.</p>
          <button onClick={() => window.location.reload()}>
            Reload Page
          </button>
        </div>
      );
    }

    return this.props.children;
  }
}
```

**Retry Logic Pattern**:
```typescript
// Example retry wrapper for dynamic imports
// File: src/core/modules/importWithRetry.ts (future task)

async function importWithRetry(
  importFn: () => Promise<any>,
  retries = 3,
  delay = 1000
) {
  try {
    return await importFn();
  } catch (error) {
    if (retries === 0) throw error;

    // Exponential backoff
    await new Promise(resolve => setTimeout(resolve, delay));
    return importWithRetry(importFn, retries - 1, delay * 2);
  }
}

// Usage in module loader:
const module = await importWithRetry(() =>
  import(`./modules/${moduleId}/index.tsx`)
);
```
