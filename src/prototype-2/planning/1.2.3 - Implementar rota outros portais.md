# Task Plan: 1.2.3 - Implementar rota "/:portalId/*" para outros portais

## Context and Objective

This task implements the dynamic routing pattern `/:portalId/*` for all portals except "main". The "main" portal uses the root path `/` (implemented in task 1.2.2), while all other portals (like "setup", "sac", etc.) must be accessible via `/:portalId/*` URLs.

**Objective**: Create a dynamic route pattern that:
- Captures any portal ID from the URL path segment
- Loads the corresponding portal configuration
- Renders the portal with its own active modules and routes
- Maintains complete isolation between portals

**Business Value**: Enables the platform to host multiple independent sub-applications (portals) under a single domain, each with its own URL namespace, modules, and configuration.

**User Impact**: Users can access different portals via clean URLs like `/setup`, `/sac/dashboard`, `/admin/users`, etc.

## Patterns Identified in Codebase

### Portal Configuration Pattern

Portal configurations are stored in `backend/src/config/portals.json`:

```json
{
  "portals": [
    {
      "portalId": "main",
      "path": "/",
      "activeModules": []
    },
    {
      "portalId": "setup",
      "path": "/setup",
      "activeModules": ["setup"]
    }
  ]
}
```

**Key observations**:
- Each portal has a unique `portalId`
- The `path` property matches the URL pattern (main: "/", others: "/:portalId")
- `activeModules` array determines which modules load in each portal

### React Router v7 Patterns

Based on `package.json`, the project uses **React Router v7.9.5**, which has updated patterns:

**Modern React Router v7 syntax**:
```typescript
import { BrowserRouter, Routes, Route } from 'react-router-dom';

// Clean, declarative routing
<BrowserRouter>
  <Routes>
    <Route path="/" element={<MainPortal />} />

```

**Key conventions**:
- Use `element` prop (not `component`)
- Use `useParams()` hook to extract URL parameters
- Wildcard `*` captures all sub-paths

### Gotchas and Pitfalls

- **React Router v7 Syntax**: Earlier versions used `component` prop, v7 uses `element` prop
- **Wildcard Matching**: The `*` in `/:portalId/*` is crucial - without it, sub-routes won't match
- **Route Order Matters**: Specific routes (like `/`) must come BEFORE dynamic routes (like `/:portalId/*`) to avoid conflicts
- **Portal ID Validation**: Always validate that the captured `portalId` corresponds to an actual portal configuration
- **Case Sensitivity**: Portal IDs are case-sensitive in URLs - be consistent

#### 1. Modify App.tsx to Add Dynamic Route

**File**: `frontend/src/App.tsx`

**Details**:
- Add `<Route path="/:portalId/*" element={<PortalLoader />} />` below the main route
- Ensure route order: specific routes first, dynamic routes last
- The wildcard `*` allows nested routes within each portal

**Pattern**: See `<Route path="/" element={<PortalLoader portalId="main" />} />` (task 1.2.2)

**Implementation**:
```typescript
import { BrowserRouter, Routes, Route } from 'react-router-dom';
import { PortalLoader } from './core/routing/PortalLoader';
import './styles/globals.css';

export default function App() {
  return (
    <BrowserRouter>
      <Routes>
        {/* Main portal - root path */}
        <Route path="/" element={<PortalLoader portalId="main" />} />

        {/* All other portals - dynamic route */}
        <Route path="/:portalId/*" element={<PortalLoader />} />
      </Routes>
    </BrowserRouter>
  );
}
```

**Why this pattern**:
- Main route (`/`) is explicit and takes priority
- Dynamic route (`/:portalId/*`) catches all other paths
- Route order prevents conflicts (SPEC-R-PR-001 to SPEC-R-PR-003)

#### 2. Enhance PortalLoader to Extract portalId from URL

**File**: `frontend/src/core/routing/PortalLoader.tsx`

**Details**:
- Import `useParams` from react-router-dom
- Extract `portalId` from URL params if not provided via props
- Validate that extracted `portalId` exists in portal configurations
- Display error if portal not found

**Implementation approach**:
```typescript
import { useParams } from 'react-router-dom';

interface PortalLoaderProps {
  portalId?: string; // Optional - if not provided, extract from URL
}

export function PortalLoader({ portalId: propPortalId }: PortalLoaderProps) {
  const { portalId: urlPortalId } = useParams<{ portalId: string }>();

  // Use prop portalId if provided, otherwise use URL param
  const portalId = propPortalId || urlPortalId;

  if (!portalId) {
    return <ErrorDisplay message="Portal ID not found" />;
  }

  // Continue with portal loading logic...
}
```

**Why this approach**:
- Supports both explicit prop (main portal) and URL param (dynamic portals)
- Single component handles all portal loading scenarios
- Clear error handling for invalid portals

### Error Handling Strategy

**Error Types**:

1. **Portal Not Found** (404):
   - User navigates to non-existent portal (e.g., `/invalid`)
   - Display: User-friendly "Portal not found" page
   - Action: Suggest navigation to main portal

2. **Portal Configuration Load Error**:
   - Network error loading portal config
   - Display: "Unable to load portal" error with retry button
   - Action: Retry button to reload configuration

3. **Module Load Error**:
   - Portal loads but module fails to load
   - Display: Error boundary within portal context
   - Action: Show error, allow other modules to continue

**Error Display Pattern**:

```typescript
// Error component for portal not found
function PortalNotFound({ portalId }: { portalId: string }) {
  return (
    <div className="flex min-h-screen items-center justify-center">
      <div className="text-center">
        <h1 className="text-4xl font-bold">Portal Not Found</h1>
        <p className="mt-4 text-muted-foreground">
          The portal "{portalId}" does not exist.
        </p>
        <a href="/" className="mt-6 inline-block underline">
          Return to Home
        </a>
      </div>
    </div>
  );
}
```

---

**Implementation Notes**:

1. **Route Order Critical**: The order of routes in `App.tsx` matters. Main route (`/`) MUST come before dynamic route (`/:portalId/*`) to ensure correct matching (SPEC-R-PR-001).

2. **Wildcard Required**: The `*` in `/:portalId/*` is essential. Without it, only exact matches like `/setup` would work, but sub-routes like `/setup/modules` would fail.

3. **Portal ID Validation**: Always validate that the captured `portalId` exists in the portal configuration before attempting to load modules. This prevents confusing errors later.

4. **Consistent Naming**: Portal IDs are case-sensitive. Ensure consistency between configuration files and URL navigation.

5. **Error Boundaries**: Each portal should have its own error boundary to prevent one portal's errors from affecting others.

6. **Future Integration**: This task lays groundwork for JQEL-based portal configuration loading (task 1.4.x) and dynamic module loading (task 2.1.x).
