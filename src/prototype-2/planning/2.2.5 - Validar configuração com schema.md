# Task Plan: 2.2.5 - Validar configuração com schema

## Context and Objective

Implement schema-based validation for instance configurations, ensuring that the `config` field of each instance adheres to the structure defined by its module. This task enhances data integrity by validating module-specific configuration parameters against JSON schemas, providing real-time feedback during instance creation and editing.

**Business Value:** Prevents configuration errors before they cause runtime issues, reduces support burden, and ensures consistent module behavior across instances.

**User Impact:** Users receive immediate feedback when entering invalid configurations, with clear error messages explaining what's wrong and how to fix it, reducing trial-and-error and improving confidence.

### Reusable Code Examples

**Dynamic Zod Schema Pattern:**
```typescript
// Create Zod schema from module schema definition
function createConfigSchema(moduleSchema: ModuleConfigSchema): z.ZodObject<any> {
  const shape: Record<string, z.ZodTypeAny> = {};

  for (const [key, fieldSchema] of Object.entries(moduleSchema.properties)) {
    let zodType: z.ZodTypeAny;

    switch (fieldSchema.type) {
      case 'string':
        zodType = z.string();
        if (fieldSchema.minLength) zodType = (zodType as z.ZodString).min(fieldSchema.minLength);
        if (fieldSchema.maxLength) zodType = (zodType as z.ZodString).max(fieldSchema.maxLength);
        break;
      case 'number':
        zodType = z.number();
        if (fieldSchema.min) zodType = (zodType as z.ZodNumber).min(fieldSchema.min);
        if (fieldSchema.max) zodType = (zodType as z.ZodNumber).max(fieldSchema.max);
        break;
      case 'boolean':
        zodType = z.boolean();
        break;
      case 'object':
        zodType = z.record(z.unknown());
        break;
      default:
        zodType = z.unknown();
    }

    if (fieldSchema.required) {
      shape[key] = zodType;
    } else {
      shape[key] = zodType.optional();
    }
  }

  return z.object(shape);
}
```

### Gotchas and Pitfalls

- ⚠️ **Schema format choice**: Decide between JSON Schema (standard) vs Zod schema (TypeScript-native). JSON Schema is more portable, Zod is more developer-friendly.
- ⚠️ **Schema storage**: Schemas should be stored in module manifest or separate schema files. For now, use inline schemas in modules.json.
- ⚠️ **Dynamic schema loading**: Schemas must be fetched before form renders, or use loading state.
- ⚠️ **Backward compatibility**: If a module doesn't define a schema, validation should be permissive (allow any valid JSON).
- ⚠️ **Schema versioning**: Module schema may change over time; consider version matching.
- ⚠️ **Complex types**: Nested objects, arrays, and unions require recursive schema generation.
- ⚠️ **Performance**: Dynamic schema creation should be cached, not recreated on every render.
- ⚠️ **Error messages**: Zod default errors may be technical; map to user-friendly messages.

### Existing Patterns to Follow

- **Validation integration**: Extend existing Zod schema in `instanceSchema.ts`
- **Async validation**: Use React Hook Form async validation mode if schema fetch is slow
- **Error display**: Use FormFieldError component for per-field errors
- **Fallback behavior**: If schema unavailable, accept any valid JSON object

```
   - If not:
     - Use permissive schema (z.record(z.unknown()))

4. Compose into instance validation schema
   - Merge dynamic config schema with base instance schema
   - Update React Hook Form resolver

User enters config data

5. Validate on blur/change
   - React Hook Form calls Zod schema.parse(data.config)
   - If valid: No errors
   - If invalid: Extract field errors

6. Display validation errors
   - Map Zod errors to field paths
   - Render FormFieldError for each invalid field
   - Show user-friendly error messages

User submits form

7. Final validation
   - Full schema validation runs
   - If valid: Proceed with mutation
   - If invalid: Show errors, prevent submit
```

### Error Handling Strategy

**Error Types:**

- **Schema fetch error**:
  - Fallback: Use permissive validation (accept any JSON)
  - Display: Info message "Using basic validation (schema unavailable)"
  - Log error to console

- **Invalid schema definition**:
  - Fallback: Use permissive validation
  - Display: Warning "Module schema is invalid, using basic validation"
  - Log error to console for developer

- **Schema validation errors** (user input):
  - Display: Per-field errors via FormFieldError
  - Message: User-friendly (e.g., "Must be at least 3 characters" instead of "String must contain at least 3 character(s)")

- **Schema generation error** (code bug):
  - Fallback: Use permissive validation
  - Display: Generic error "Validation error, please check your input"
  - Log error to console
  - Report to error tracking (if available)

**Error Display Pattern:**
```typescript
// Schema fetch error
if (isLoadingSchema) {
  return <Skeleton />; // Show loading
}

if (moduleSchemaError) {
  console.error('Failed to load module schema:', moduleSchemaError);
  // Proceed with permissive validation
}

// Field validation errors
<FormField
  control={form.control}
  name="config.theme"
  render={({ field, fieldState }) => (
    <FormItem>
      <FormLabel>Theme</FormLabel>
      <FormControl>
        <Select {...field}>...</Select>
      </FormControl>
      {fieldState.error && (
        <FormMessage>
          {getUserFriendlyError(fieldState.error)}
        </FormMessage>
      )}
    </FormItem>
  )}
/>
```
