# Task Plan: 2.2.3 - Implementar health check Backend

## Context and Objective

Implement Backend (Express server) health check functionality for the Setup Module. This provides a self-check mechanism for the Backend service itself, reporting on its operational status, uptime, and basic system metrics.

**Business Value**: Completes the health monitoring triad (n8n, Redis, Backend), giving administrators a complete view of platform infrastructure health in one place.

**User Impact**: Administrators can verify the Backend service is operational and monitor its performance metrics (uptime, memory usage, response time) directly from the Platform Settings view.

**Integration**: This health check will be displayed in the Platform Settings view of the Setup Module (SPEC-MS-PS-013, SPEC-MS-PS-014:016) as the third and final health indicator alongside n8n and Redis.

### Gotchas and Pitfalls

- ⚠️ Backend health check is always synchronous and fast - no network calls needed
- ⚠️ Memory usage metrics are point-in-time - don't show trends (consider adding if needed)
- ⚠️ Backend can report "ok" even if dependencies (n8n, Redis) are down - that's expected (separate checks)
- ⚠️ Uptime resets on server restart - this is informational, not an error condition
- ⚠️ Don't confuse "backend health" with "overall platform health" - they're different
- ⚠️ Memory metrics may be confusing to non-technical users - provide clear labels

### Data Flow

```
Frontend (PlatformSettings)
    ↓ useHealth('backend')
    ↓ (polling every 60s - same as n8n and Redis)
    ↓
healthClient.check('backend')
    ↓ GET /api/health/backend (or /api/health)
    ↓
Backend (health.routes.ts)
    ↓ gathers system metrics (uptime, memory, version)
    ↓ responds immediately (no external calls)
    ↓
Response flows back to frontend
    ↓
Frontend displays indicator (typically always green unless server is down)
```

### Error Handling Strategy

**Error Types:**
- **Network error** (frontend can't reach backend): Display red indicator "Backend unreachable"
- **Backend crash**: Frontend will detect failed requests and show red indicator
- **Timeout**: Very unlikely for self-check, but handle as "Backend slow"

**Note:** If Backend is down, the frontend typically cannot load at all. However, the health indicator helps verify Backend is operational when troubleshooting or after a restart.

**Error Display Pattern:**
```typescript
// Same pattern as tasks 2.2.1 and 2.2.2
<HealthIndicator
  service="Backend"
  status={backendHealth.data?.status || 'loading'}
  error={backendHealth.error?.message}
  lastCheck={backendHealth.dataUpdatedAt}
/>
```

**Backend Response:**
```typescript
// Backend always returns 200 OK if it's running
router.get('/health/backend', (_req: Request, res: Response) => {
  try {
    const memoryUsage = process.memoryUsage();

    res.status(200).json({
      status: 'ok',
      timestamp: new Date().toISOString(),
      uptime: process.uptime(),
      version: process.env.npm_package_version || '1.0.0',
      environment: process.env.NODE_ENV || 'unknown',
      memory: {
        heapUsed: Math.round(memoryUsage.heapUsed / 1024 / 1024),
        heapTotal: Math.round(memoryUsage.heapTotal / 1024 / 1024),
        rss: Math.round(memoryUsage.rss / 1024 / 1024),
      },
      nodeVersion: process.version,
    });
  } catch (error: any) {
    // Extremely unlikely, but handle gracefully
    res.status(500).json({
      status: 'down',
      error: error.message,
      timestamp: new Date().toISOString(),
    });
  }
});
```

// Helper function to format uptime
function formatUptime(seconds: number): string {
  const hours = Math.floor(seconds / 3600);
  const minutes = Math.floor((seconds % 3600) / 60);

  if (hours > 24) {
    const days = Math.floor(hours / 24);
    return `${days}d ${hours % 24}h`;
  }
  return `${hours}h ${minutes}m`;
}

// Usage in HealthIndicator
