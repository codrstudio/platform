# Task Plan: 1.3.2 - Implementar /api/1/auth/refresh

## Context and Objective

### What will be implemented
This task validates and ensures full SPEC compliance of the `/api/1/auth/refresh` endpoint in the Backend layer. The endpoint is already implemented in `auth.routes.ts` with token rotation and reuse detection, but this task focuses on:
1. Verifying all SPEC-AU-RF-* requirements are met
2. Adding any missing validation or error handling
3. Ensuring proper n8n integration pattern (even though current implementation is Backend-only)
4. Documenting deviation from SPEC (Backend handles refresh instead of n8n)
5. Adding comprehensive tests and validation

### Why it's needed
The refresh endpoint is critical for session continuity and security. It must:
- Rotate refresh tokens to prevent long-lived token exposure
- Detect and respond to token reuse (security breach indicator)
- Maintain token families for breach detection
- Provide seamless user experience with automatic token renewal

### How it integrates
The `/api/1/auth/refresh` endpoint integrates with multiple platform components:
- **Frontend**: Auto-renewal logic calls this endpoint before access token expires
- **Redis**: Stores token metadata for validation and family tracking
- **JWT Service**: Generates new access tokens with proper claims
- **Token Rotation Service**: Manages token lifecycle and security
- **n8n (Future)**: Current implementation is Backend-only, but SPEC requires n8n integration

### Business value
- Maintains user sessions without frequent re-authentication
- Protects against token theft through rotation and reuse detection
- Provides security incident response (family revocation on breach)
- Meets OAuth 2.0 security best practices

### User impact
Users experience seamless authentication - their sessions stay active as long as they're using the app, with automatic renewal happening invisibly in the background. If a security breach is detected, all sessions are terminated to protect the user.

### Gotchas and Pitfalls

**SPEC Deviation - Backend vs. Backbone:**
- ⚠️ **SPEC-AU-AR-001**: "Autenticação DEVE ser responsabilidade do Backbone (n8n)"
- ⚠️ **SPEC-AU-RF-005**: "Backend DEVE repassar ao Backbone"
- **Current Reality**: Backend handles refresh entirely, doesn't proxy to n8n
- **Reason**: Direct Redis access is faster and simpler for token operations
- **Action Required**: Document this architectural decision and create migration plan

**Token Reuse Detection Timing:**
- ⚠️ Token must be marked as consumed AFTER validation but BEFORE generating new tokens
- ⚠️ If marked too early, legitimate concurrent requests might trigger false reuse detection
- ⚠️ If marked too late, actual reuse might slip through
- **Pattern**: See existing implementation in auth.routes.ts lines 94-96

**Family Revocation Performance:**
- ⚠️ Revoking a token family requires multiple Redis operations (get + setex per token)
- ⚠️ Large families (many rotations) could cause latency spikes
- ⚠️ Current implementation is NOT pipelined optimally (sequential gets)
- **Improvement**: Consider pipelining Redis operations in tokenRotation.service.ts

**Cookie vs. Body Priority:**
- ⚠️ SPEC-AU-RF-003: "Se ambos presentes, body tem prioridade"
- ⚠️ Current implementation: `req.body.refresh_token || req.cookies?.refresh_token`
- ✓ This is correct - body is checked first due to || operator

**Error Status Codes:**
- ⚠️ SPEC-AU-RF-018: Invalid/expired token → HTTP 401
- ⚠️ SPEC-AU-RF-019: Reuse detected → HTTP 401
- ⚠️ Redis errors → HTTP 500 (internal error)
- ✓ Current implementation handles all cases correctly

## Technical Specification

### Architecture

**Current Implementation (Backend-only):**
```
Frontend → Backend /api/1/auth/refresh → Redis (validation)
                ↓                              ↓
           JWT Service                   Token Rotation
                ↓                              ↓
           Access Token                  New Refresh Token
                ↓                              ↓
           Response (200/401/500) ← ← ← ← ← ← ←
```

**SPEC-Compliant Architecture (Future):**
```
Frontend → Backend → n8n Workflow → Redis
              ↓           ↓             ↓
         Proxy Only   Business    Token Storage
                       Logic
```

### Data Flow

**Request Flow:**
```
1. Frontend sends POST /api/1/auth/refresh
   Body: { refresh_token: "..." } OR Cookie: refresh_token=...

2. Backend extracts token (body priority)

3. Backend validates token via tokenRotationService
   - Hash token with SHA-256
   - Check Redis for token metadata
   - Validate: exists, not expired, not revoked, not consumed

4. If REUSED:
   - Log security event
   - Revoke entire token family
   - Return 401 with "token_reused" code

5. If VALID:
   - Mark token as consumed (prevent future reuse)
   - Generate new JWT access token
   - Generate new opaque refresh token
   - Store new refresh token (same family)
   - Return 200 with new tokens

6. If INVALID:
   - Return 401 with specific error code
   - (NOT_FOUND, EXPIRED, REVOKED)
```

**Token Rotation Chain:**
```
Initial Login:
  Family ID: abc123
  Token 1 (active)

First Refresh:
  Family ID: abc123 (same)
  Token 1 (consumed) → Token 2 (active)

Second Refresh:
  Family ID: abc123 (same)
  Token 2 (consumed) → Token 3 (active)

Token Reuse (Token 1 used again):
  Detect: Token 1 has consumed_at timestamp
  Action: Revoke entire family abc123
  Result: Tokens 1, 2, 3 all revoked
```

```markdown
**Pros:**
- Faster token refresh (better UX)
- Simpler debugging and logging
- Fewer failure points

**Cons:**
- Violates SPEC architecture separation
- Token logic duplicated between Backend and n8n
- Harder to share refresh logic across services

### Migration Path
See docs/n8n-integration-plan.md for eventual SPEC compliance.
```

**Create**: `src/prototype-2/backend/src/middleware/validateRefreshRequest.middleware.ts`

**Purpose**: Centralize request validation for better code organization

**Content:**
```typescript
import { Request, Response, NextFunction } from 'express';

/**
 * Validates /api/1/auth/refresh request
 *
 * SPEC References:
 * - SPEC-AU-RF-001: Accept refresh_token in body
 * - SPEC-AU-RF-002: Accept refresh_token in cookie
 * - SPEC-AU-RF-003: Body has priority
 * - SPEC-AU-RF-004: Token must be string
 */
export const validateRefreshRequest = (
  req: Request,
  res: Response,
  next: NextFunction
): void => {
  // Extract token (body priority)
  const refreshToken = req.body.refresh_token || req.cookies?.refresh_token;

  // Check presence
  if (!refreshToken) {
    res.status(401).json({
      code: 'missing_token',
      message: 'Refresh token is required',
    });
    return;
  }

  // Check type
  if (typeof refreshToken !== 'string' || refreshToken.trim().length === 0) {
    res.status(401).json({
      code: 'invalid_token_format',
      message: 'Refresh token must be a non-empty string',
    });
    return;
  }

  // Attach to request for handler
  req.refreshToken = refreshToken;
  next();
};

// Extend Express Request type
declare global {
  namespace Express {
    interface Request {
      refreshToken?: string;
    }
  }
}
```

### Error Handling Strategy

**Error Types and Responses:**

| Error Type | HTTP Status | Error Code | Message | Cause |
|------------|-------------|------------|---------|-------|
| Missing Token | 401 | missing_token | Refresh token is required | No token in body or cookie |
| Invalid Format | 401 | invalid_token_format | Token must be non-empty string | Token is not a string |
| Invalid Token | 401 | invalid_token | Refresh token is invalid or expired | Token not found in Redis |
| Expired Token | 401 | token_expired | Refresh token has expired | Token.expires_at < now |
| Revoked Token | 401 | token_revoked | Refresh token has been revoked | Token.revoked = true |
| Reused Token | 401 | token_reused | Token has been reused. All sessions revoked. | Token.consumed_at exists |
| Redis Error | 500 | internal_error | Failed to validate token | Redis connection/operation failed |

**Error Logging Pattern:**
```typescript
// Security events (WARN level)
console.warn('⚠️ Token reuse detected', {
  userId: validation.data.user_id,
  familyId: validation.data.family_id,
  tokenHash: validation.data.token_hash.substring(0, 16) + '...',
  ip: req.ip,
  userAgent: req.get('user-agent'),
});

// Errors (ERROR level)
console.error('❌ Error in /auth/refresh:', error);
```

**Error Boundary:**
All unhandled errors are caught by Express error handler middleware:
- File: `src/prototype-2/backend/src/middleware/errorHandler.middleware.ts`
- Pattern: `next(error)` passes to centralized handler
- Response: Structured JSON with code, message, details (dev only)
