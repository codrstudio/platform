# Task Plan: 1.7.7 - Implementar header X-Platform-Key

## Context and Objective

This task implements the `X-Platform-Key` header for Backend → n8n communication, completing the mutual authentication between the Platform and n8n Backbone. This header ensures secure communication by validating that requests originate from authorized systems.

**What will be implemented**: Add `X-Platform-Key` header to all outgoing requests from Backend to n8n webhooks, using the shared secret from environment configuration.

**Why it's needed**: Mutual authentication prevents unauthorized access to n8n workflows. Without this header, any system knowing the webhook URLs could trigger workflows, creating security vulnerabilities.

**How it integrates**:
- Backend already has `N8N_SHARED_SECRET` in config (from env.ts)
- n8nProxy.service.ts already sends the header (line 119)
- This task documents and validates the implementation is complete
- Complements task 1.7.8 which validates incoming headers from n8n → Backend

**Business value**: Ensures only authorized platform components can invoke n8n workflows, protecting business logic and data access from unauthorized use.

**User impact**: Transparent to users - security hardening happens at the infrastructure level without affecting user experience.

### Gotchas and Pitfalls

**Header Case Sensitivity**:
- HTTP headers are case-insensitive per RFC 7230
- Use exact case `X-Platform-Key` for consistency
- n8n may be case-sensitive in validation - verify exact match

**Secret Validation**:
- ⚠️ Secret MUST be at least 32 characters (enforced in env.ts)
- ⚠️ Secret MUST be same on both sides (Backend and n8n)
- ⚠️ Mismatch causes all requests to fail with 401

**Environment Variable Name Confusion**:
- Backend uses `N8N_SHARED_SECRET` (for sending to n8n)
- n8n uses `PLATFORM_SHARED_SECRET` (for validating from Backend)
- **Both must have the same value** (SPEC-CF-VE-018)

**Empty or Missing Secret**:
- Validated at startup - server won't start if missing
- No need for runtime checks
- Better to fail fast than silently accept insecure config

**Logging Secrets**:
- ⚠️ NEVER log the secret value (SPEC-CF-SEC-002)
- Only log "header present/absent" for debugging
- Use structured logging without exposing values

## Implementation Notes

### Why Two Separate Secrets?

The platform uses two environment variables for clarity:

1. **N8N_SHARED_SECRET**: Used when Backend → n8n (sending requests)
   - Included as `X-Platform-Key` header
   - Validated by n8n webhooks

2. **PLATFORM_SHARED_SECRET**: Used when n8n → Backend (receiving requests)
   - Validated from incoming `X-Platform-Key` header (task 1.7.8)
   - Compared against this secret

**They must have the same value** (SPEC-CF-VE-018), but separate variables make code clearer:
- "Which secret do I use to send to n8n?" → `N8N_SHARED_SECRET`
- "Which secret do I use to validate from n8n?" → `PLATFORM_SHARED_SECRET`

### Why Validate Equality?

Without equality validation:
- Developer might set different values by mistake
- One direction would fail authentication
- Hard to debug (works one way, not the other)

With equality validation:
- Startup fails immediately if misconfigured
- Clear error message guides fix
- Prevents silent failures in production
