# Task Plan: 2.2.4 - Implementar remoção de portal

## Context and Objective

Implement the portal deletion functionality within the Setup module, allowing administrators to safely remove portals with proper confirmation, validation, and cascade handling. This is a destructive operation requiring careful UX and backend coordination.

**Business Value:** Enables platform administrators to decommission portals and maintain a clean configuration as the platform evolves.

**User Impact:** Provides a safe, guided deletion process with clear warnings about consequences, preventing accidental data loss and configuration corruption.

**Integration:** Integrates with portal listing (Task 2.2.1) for delete button access, uses JQEL mutations with optimistic updates, and implements proper cascade handling (deactivate modules, remove instances).

// Delete hook already implemented
export function useDeletePortal() {
  return useOptimisticMutation<void, string, Error, Portal[]>({
    mutationFn: deletePortal,
    optimistic: {
      queryKeys: ['backend', 'portal'],
      updater: (portals: Portal[] | undefined, portalId) => {
        if (!portals) return [] as Portal[];
        return removeItemFromList(portals, portalId, 'portalId');
      },
      invalidateOnSettled: true
    }
  });
}
```

### Gotchas and Pitfalls

- **Portal "main" protection:** CANNOT be deleted (removable=false) - SPEC-C-P-020, SPEC-MS-FU-005
  - Hide/disable delete button for "main" portal
  - Backend MUST also validate (double protection)
- **Cascade deletion:** Removing portal MUST:
  - Deactivate ALL modules in that portal (SPEC-C-P-023)
  - Remove ALL instances of those modules (SPEC-C-P-024)
  - This happens on backend - frontend just triggers deletion
- **Consequences display:** MUST show user what will be deleted (SPEC-MS-FB-004)
  - List modules that will be deactivated
  - List instances that will be removed
  - Get this info BEFORE showing dialog (fetch counts or details)
- **Optimistic updates:** Delete hook already implements
  - Portal removed from UI immediately
  - Rolled back if backend fails
- **No undo:** Once deleted, portal configuration is lost
  - Make confirmation dialog VERY clear
  - Consider adding "type portal name to confirm" pattern for extra safety

### Data Flow

```
User clicks "Delete" on portal card
    ↓
Check: portal.removable === true?
    ↓ (if false)
    Show tooltip: "Cannot delete this portal"
    ↓ (if true)
    PortalDeleteDialog opens
    ↓
Dialog fetches consequence data:
- Active modules count
- Instance count
    ↓
Display consequences to user
    ↓
User clicks "Cancel" → Close dialog, no action
    ↓
User clicks "Confirm Delete"
    ↓
useDeletePortal mutation called
    ↓
Optimistic update (portal removed from UI immediately)
    ↓
JQEL mutation sent to backend
{schema: 'backend', mutate: 'portal', action: 'delete', where: {portalId}}
    ↓
Backend:
1. Validate removable=true
2. Deactivate all modules
3. Remove all instances
4. Delete portal from config/portals.json
    ↓
Success response
    ↓
TanStack Query invalidates cache
    ↓
Toast notification: "Portal deleted successfully"
    ↓
Dialog closes
```

const deletePortalMutation = useDeletePortal();

const handleConfirmDelete = () => {
  if (!portalToDelete) return;

  deletePortalMutation.mutate(portalToDelete.portalId, {
    onSuccess: () => {
      toast({ title: 'Portal deleted successfully' });
      setDeleteDialogOpen(false);
      setPortalToDelete(null);
    },
    onError: (error) => {
      toast({
        title: 'Failed to delete portal',
        description: error.message,
        variant: 'destructive'
      });
    }
  });
};
```

### User Journey

1. **User hovers over delete button** → Tooltip shows (if portal not removable: "Cannot delete")
2. **User clicks delete** → Validation check (removable?)
3. **Dialog opens** → Shows confirmation with consequences
4. **User reads consequences** → Sees modules and instances that will be affected
5. **User decides:**
   - **Cancel** → Dialog closes, no action taken
   - **Confirm** → Deletion proceeds
6. **Deleting state** → Button shows loading, dialog cannot be closed
7. **Success** → Toast notification, dialog closes, portal removed from list
8. **Error** → Toast with error message, dialog remains open for retry

### Error Handling Strategy

**Error Types:**

**Non-Removable Portal Deletion Attempt:**
```typescript
// Frontend validation (before showing dialog)
const handleDeleteClick = (portal: Portal) => {
  if (!portal.removable) {
    toast({
      title: 'Cannot delete portal',
      description: `The portal "${portal.name}" is marked as non-removable and cannot be deleted.`,
      variant: 'destructive'
    });
    return;
  }
  // Proceed to show dialog
};
```

**Backend Rejection:**
```typescript
// Backend should also validate
deletePortalMutation.mutate(portalId, {
  onError: (error) => {
    if (error.code === 403) {
      toast({
        title: 'Operation not allowed',
        description: 'This portal cannot be deleted.',
        variant: 'destructive'
      });
    } else if (error.code === 404) {
      toast({
        title: 'Portal not found',
        description: 'The portal has already been deleted.',
        variant: 'destructive'
      });
    } else {
      toast({
        title: 'Failed to delete portal',
        description: error.message,
        variant: 'destructive'
      });
    }
    // Dialog stays open for potential retry
  }
});
```

**Network Error:**
- TanStack Query handles retry logic
- Show error toast with generic message
- Dialog remains open for user to retry

**Optimistic Update Rollback:**
- If deletion fails, TanStack Query rolls back optimistic update
- Portal reappears in list
- Error toast explains what happened
